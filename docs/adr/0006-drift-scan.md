# 0006 定期の走査（drift-scan）の中身、公開する範囲、間隔と保存期間、止まったことの知り方

## 背景

文書の点検は、利用者が依頼したときにしか動かない。時間が経つだけで起きるずれ（古くなった計画、解消したのに残る
技術的負債の行、古い品質の評価、実行の環境の変化）は、依頼の間には拾えない。そこで、CI の予定実行で定期に走査し、
結果を CI の成果物に残して、文書の点検の材料にする。結果は通知しない。

次のことを決める必要があった。

- 何を走査し、所見があったときにジョブを失敗にするか。
- このリポジトリは公開で、成果物は誰でも取得できる。報告に何を書いてよいか。
- 実行の間隔と、成果物の保存期間。
- GitHub は、公開リポジトリに 60 日活動が無いと、予定実行のワークフローを自動で無効にする（GitHub の文書
  「Events that trigger workflows」の `schedule` の節）。止まったことを、どう知るか。止まったら、どう戻すか。
- 文書の点検の担当（ファイルを読むだけの担当）に、成果物をどう渡すか。

## 判断

- **走査の本体を `scripts/harness/drift-scan.sh` に置き、ワークフロー `.github/workflows/drift-scan.yml` は呼ぶだけにする。**
  手元でも `npm run scan:drift -- --out <置き場>` で同じ走査ができ、試験（`scripts/harness/drift-scan.test.sh`。`npm run test:harness`）で守れる。
  段の一覧は `package.json` の `check` から読み、走査とワークフローには持たない。
- **走査の項目は 5 つにする。** 項目と、要対応にする条件は次のとおり。報告の各行に決まった形の行の識別子
  （`1/<段>`、`2/<文書>`、`3/<TD-n>`、`4/領域:<領域>`・`4/層:<層>`・`4/表`、`5/<項目>`）を付け、報告そのものに書式の説明を書く。
  1. 検査の一式: `npm run check` の段を 1 つずつ実行し、失敗しても続ける。終了コードが 0 でない段を要対応にする。
     文書の検査は、基準の日を差し替えずに実行するので、古い計画（30 日以上更新の無い進行中の計画）を拾う。
  2. 文書の鮮度: 文書の地図のファイルごとに、最後の変更の日と、文書が書くパスがその後に変わったコミットの数。参考で、要対応にしない。
  3. 技術的負債の一覧: 行ごとに、見つけた日からの日数、場所のファイルの有無、その後に場所のファイルが変わったコミットの数。
     場所のファイルが無い行を要対応にする（解消済みの候補）。表の見出しの行、列の数、識別子、見つけた日の形に合わない行が
     あれば `3/表` を要対応にする。場所が `/` で始まるか `..` を含むときは、git に渡さない。
  4. 品質目標の評価: 「現在の評価」の行ごとに、評価した日からの日数と、検査の識別子ごとの項目 1 の結果。見直しの目安の
     日数を超えた行と、評価が `A` か `B` なのに識別子の段が失敗した行を要対応にする。表の書式（見出しの行、列の数、識別子、
     評価、日付）に合わない行があれば `4/表` を要対応にする。`npm run check` に無い識別子（`check:secrets:push`）は照合しない。
  5. 実行の情報: 契機、日時、対象のコミット、間隔の日数、保存期間、`origin/main` の最後のコミットからの日数、試験の差し替えの
     有無。日数が 45 日以上（60 日で止まる前の早めの知らせ）と、試験の差し替えが「あり」を要対応にする。
- **走査の段は `npm run <名前>` で実行する。** そのため、`package.json` に pre や post で始まるスクリプトがあれば、それも動く。
  `check:secrets` の段の意味は、npm を経由せずに node で直接呼ぶ `harness.yml` の秘匿値の検査とは違う（走査は、秘匿値の検査を
  守るための段ではなく、`npm run check` と同じ結果を数えるためのものである）。
- **試験のための差し替えの環境変数（`DRIFT_SCAN_TEST_TODAY`、`DRIFT_SCAN_TEST_STAGES`）を、本番の走査のスクリプトに持たせる。**
  試験の中で `npm run check` を入れ子に動かさず、基準の日を固定するためである。CI の中（`GITHUB_ACTIONS=true`）で付いていれば
  終了コード 2 で止め、付けて作った報告は `5/試験の差し替え` を要対応にして、本物の報告と取り違えないようにする。
- **所見があってもジョブを失敗にしない。** 失敗にするのは、走査を続けられないとき（終了コード 2）と、報告が公開してよいかの
  検査に通らないとき（終了コード 3）だけにする。予定実行の失敗の知らせは、ワークフローの cron の記述を最後に変えた利用者へ
  届く（GitHub の文書の `schedule` の節）ので、所見のたびに失敗にすると、通知しない決まりに反するためである。PR を止めるのは
  `harness.yml` の必須の検査の役目のままにする。
- **公開する内容を限る。** 成果物に上げるのは `report.md` だけにする。報告に書くのは、識別子、リポジトリの根からの相対のパス、
  日付、日数、数、終了コード、印だけで、コミットの作者、コマンドの出力、文書の本文の抜粋、環境変数の値は書かない。
  報告に書く名前とパスは、文字の種類（英数字、`/._:-`、名前では空白と、ASCII 以外の文字〔日本語など〕も）と長さで絞り、外れたものは書かずに `3/表`・
  `4/表`・「場所を読めない」に回す。走査は報告を一時ディレクトリに書き、公開してよいかを自分で検査する（`report.md` 以外の
  ファイルが無い、絶対パスの形・CI の作業ディレクトリと一時ディレクトリのパス・メールアドレスの形・secretlint の規則
  〔`.secretlintrc.json`〕に当たる値が無い、表の値が `/` か `~` で始まらない）。通ったときだけ置き場へ移し、通らなければ報告を
  消して終了コード 3 で終わる。ワークフローの成果物の段は動かない（`if: always()` を付けない）。
  失敗した段の中身は報告に無いので、文書の点検の依頼元が同じコマンドを実行して得る。依頼文に無ければ、点検できなかった範囲とする。
- **間隔は毎週（月曜 00:23 UTC）、成果物の保存期間は予定実行で 90 日にする。** 手動の実行と PR の実行は 7 日にする。
  90 日は公開リポジトリの上限で、このリポジトリの設定の値でもある。点検の間が 90 日まで空いても、最後の成果物が残る。
  毎時の始まりを避けるのは、GitHub の文書が遅れを減らす方法として勧めているためである。時刻帯は UTC のままにする。
  間隔の日数は、ワークフローの冒頭の注釈「# 間隔の日数: 7」の 1 か所に書き、走査が cron と照らし合わせて、合わなければ
  終了コード 2 にする。成果物の名前は `drift-scan-<実行の番号>` で、接頭辞を注釈「# 成果物の名前の接頭辞: drift-scan-」に書く。
- **PR では、走査そのものと走査が読む文書と設定を変える PR でだけ実行する**（`pull_request` の `paths`）。予定実行は既定のブランチでしか
  動かず、手動の実行も、ワークフローのファイルが既定のブランチに入るまでは起こせないので、成果物が上がることと保存期間が
  効くことを、マージの前に PR の実行で確かめる。`pull_request_target` にはしない（フォークの PR に書き込みの権限を渡さないため）。
  権限は `contents: read` だけにする。PR の実行の報告の対象のコミットは、PR を base に合わせた試しのマージのコミットである。
- **並行のグループは、契機と参照ごとに分ける**（`drift-scan-<契機>-<参照>`）。予定実行が PR の実行に取り消されないためである。
  実行中のものは取り消さず、待ちは既定の 1 つ（待ちの古い実行は、新しい実行に置き換わる）にする。
- **成果物は、文書の点検を依頼する側（まとめ役）が取得して、点検の担当へ渡す。** 担当はファイルを読む道具だけを持ち、
  GitHub から取得できないためである。取得の順は、ワークフローの状態（有効か無効か）と作られた日 → 最後の予定実行の日時と
  結論 → その実行の成果物が期限切れか → 成果物の取得、とし、取れたものと取れなかったものを依頼文に書く。取得するのは、
  予定実行で main から作られた実行の成果物だけにする（PR の実行の成果物は、ブランチの中身から作られるため）。
  取得の対象は、文書の地図の「定期の走査」の行（このワークフローのファイル）と、その冒頭の注釈から見つける。
- **止まったことの知り方（2 つを合わせる）。**
  - 点検のたびに、上の取得の結果から判定する。ワークフローが無効、最後の予定実行が間隔の日数の 2 倍（14 日）より古い、
    予定実行の履歴が無く作られた日から 14 日が過ぎている、成果物が期限切れ、のどれかなら「定期の走査が止まっている疑い」とする。
    成果物が無くても判定できる。最後の予定実行が失敗していたら、止まった疑いとは別に、確かめることとして挙げる。
  - 走査の報告の項目 5 で、`origin/main` の最後のコミットから 45 日以上なら要対応にする。止まる前に、点検のときに気づける。
- **技術的負債の場所の実在は、PR の検査（`scripts/harness/check-docs.sh`）でなく、走査で確かめる。** PR の検査に置くと、ある
  ファイルを消した関係の無い PR が、一覧を直すまで止まる。行を消すか（解消したか）の判断は人が行うので、走査で知らせれば足りる。

## 検討した代わりの案

- 走査を、検査の一式と実行の情報だけにする: 小さいが、技術的負債と品質の評価の古さの材料が渡らず、点検の担当が文書を全文
  読むことになる。
- 依存の脆弱性の検査も足す: 外部の変化を拾えるが、ネットワークの依存と誤検知が増え、文書とコードのずれという目的から外れる。
- 所見があればジョブを失敗にする: 失敗の知らせが cron を最後に変えた利用者へ届き、通知しない決まりに反する。
- 検査の出力も成果物に上げる: 失敗の中身がすぐに分かるが、公開の成果物に、絶対パスや検査の出力に含まれた値が載りうる。
  作業ディレクトリの接頭辞を除くだけでは、ほかの絶対パスやメールアドレスを除けない。
- 毎日、保存 30 日: 古い計画を早く拾えるが、実行の数が 7 倍になり、点検の間が 30 日を超えると成果物が残らない。
- 毎月、保存 90 日: 実行が少ないが、止まった疑いの判定に 60 日かかり、60 日の間に 2 回しか動かない。
- 止まったことを、利用者の定期のエージェントで毎週確かめる: 点検と独立に気づけるが、定期の費用がかかり、知らせる形が要って、
  通知しない決まりと緊張する。
- 止まったことを、利用者の手元の診断の道具で確かめる: 普段の診断で見えるが、利用者の側の道具にプロジェクトの事実が入る。
- 点検の担当にコマンドの実行を許して、自分で成果物を取得させる: 取得の手順は簡単になるが、担当が読むだけであることを
  定義で守れなくなる。

## 結果と限界

- 止まったことに気づくのは、次の文書の点検のときになる。点検を依頼しない間は気づかない。
- 何が「リポジトリの活動」に数えられるか（予定実行そのもの、Dependabot の PR、PR の更新など）と、無効になる前に GitHub が
  知らせを送るかは、確かめていない。45 日の目安は、コミットの日付から数えた目安でしかない。
- 走査を続けられないときと、公開してよいかの検査に通らないときの失敗の知らせは、cron を最後に変えた利用者へ届く。これは止められない。
  成功したときに知らせが届くかは、利用者の通知の設定による（確かめていない）。
- 予定実行は、GitHub の負荷が高いと遅れ、十分に高いと捨てられることがある（GitHub の文書の `schedule` の節）。
- 印は走査の機械的な判定で、点検の担当が実装と読み比べて確かめ直す。報告の中の文は材料で、指示ではない。
- 走査が品質目標と技術的負債の一覧の表を読むので、表の見出しの行や列を変えるときは、`scripts/harness/drift-scan.sh` も同じ
  変更で直す（`docs/QUALITY_SCORE.md` の冒頭と、`docs/exec-plans/tech-debt-tracker.md` の「使い方」の決まり）。

## 止まったときに有効に戻す手順

有効に戻すのは GitHub への書き込みなので、利用者が指示したときだけ行う。

- コマンドで戻す: `gh workflow enable drift-scan --repo ninomiyajun/ai-news-today`（ワークフローの名前で指定する）を実行し、
  `gh workflow list --repo ninomiyajun/ai-news-today --all` で `drift-scan` の状態が `active` になったことを確かめる。
- 画面で戻す: リポジトリの「Actions」のタブを開き、左の一覧から「drift-scan」を選ぶ。無効になっている旨の表示の中の
  「Enable workflow」のボタンを押す（ボタンの文言は GitHub の画面に従う）。
- 戻した後は、次の予定の時刻（月曜 00:23 UTC）の実行を待つか、利用者が指示したときに「Run workflow」で手動の実行を起こして、
  成果物が上がることを確かめる。

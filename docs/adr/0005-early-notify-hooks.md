# 0005 早期通知のフックを公開リポジトリに置くことと、実行するプログラムの範囲

## 背景

文書の不備（地図に無いパス、切れたリンク、計画の必須の節の欠けなど）は、`npm run check` か CI を動かすまで分からなかった。
エージェントが文書を書いた直後に、文書の検査（`scripts/harness/check-docs.sh`）を動かして知らせれば、その場で直せる。
Claude Code と Codex には、道具がファイルを書いた直後にコマンドを動かす仕組み（フック）があり、定義をリポジトリに置ける
（`.claude/settings.json` と `.codex/hooks.json`）。

一方で、フックは、道具の実行の確認とサンドボックスの外で、会話を始めた人の権限で動く。このリポジトリは公開で、作業は
worktree で行うので、次の 3 つを決める必要があった。

- 実行されるフックを、公開のリポジトリに置くか。
- 別のブランチや pull request が書き換えたスクリプトを、利用者の権限で動かさないために、何を実行してよいとするか。
- 会話の中のエージェントが、フックの動かすスクリプトを書き換えられることを、どう扱うか。

## 判断

用語: 「起動元」は、フックの定義と、実行されるスクリプトのある作業ツリー。「対象」は、書いたファイルのある作業ツリー。

- **両方のツールのフックを、リポジトリに置く。** Claude Code は `.claude/settings.json`（`PostToolUse`、Edit と Write）、Codex は
  `.codex/hooks.json`（`PostToolUse`、`apply_patch`）で、どちらも `scripts/harness/notify.sh`（早期通知）を呼ぶ。`.codex/config.toml` は、
  共有したい設定が無いので置かない。
- **早期通知は知らせるだけで、作業を止めない。** 終了コードは常に 0 で、不合格、時間切れ、入力の形の変化、起動の失敗、
  上限の超過（下の「結果と限界」の上限）のときだけ、追加の文脈としてエージェントに文面を返す。文書でないファイルだけを
  書いたときと、検査が通ったときは、何も返さない。止めるのは、これまでと同じく `npm run check` と CI である。
  止める手段として、環境変数 `HARNESS_NOTIFY=off` を持つ。
- **拾うのは、ファイルを書く道具による書き込みだけにする**（Claude Code の Edit・Write と、Codex の `apply_patch`）。Bash の
  コマンドによる書き込みは拾わない。
- **起動元と対象を分け、実行するプログラムは起動元のものだけにする。** 対象にある実行できるファイル（検査のスクリプト、
  設定のプログラム、依存のパッケージ）を、起動も読み込みもしない。対象は、検査される文書としてだけ読む。起動元の根は、
  `notify.sh` の置き場から決め、呼ばれたときの作業ディレクトリに頼らない。対象の作業ツリーは、書いたファイルのパスから決め、
  起動元と git の共通のディレクトリが同じもの（同じリポジトリの作業ツリー）だけを検査する。
- **動かす検査は、文書の検査だけにする。** lint、型、試験、依存の検査、秘匿値の検査は動かさない。ESLint は、対象の
  `eslint.config.mjs` と、対象の `node_modules` の中のプラグインをプログラムとして読み込むので、対象のコードを実行する
  ことになり、上の決まりと両立しないためである。早期通知は npm を動かさないので、`package.json` のスクリプトも実行しない。
- **実行するファイルを、`notify.sh`、`notify-paths.mjs`、`check-docs.sh` の 3 つに限る。** 3 つは、ほかのファイルを読み込んで
  実行せず、`notify-paths.mjs` は `node:` で始まる組み込みのモジュールだけを読み込む（`scripts/harness/notify.test.sh` が検索で
  確かめる）。
- **起動元は、Claude Code では会話を始めた作業ツリー、Codex では本体の作業ツリーにする。** Codex は、worktree で始めた
  会話でも、フックの定義を本体の作業ツリーから読むためである。Codex のフックのコマンドは、本体の作業ツリーのスクリプト
  だけを実行する。
- **Codex のフックのコマンドは、実行の前に確かめる。** 本体が裸のリポジトリでないこと、3 つのスクリプトがコミットされた版
  （`HEAD`）にあること、`scripts/harness/` の下が `HEAD` から変わっていないことを確かめ、どれかが成り立たなければ、スクリプトを
  動かさずに「早期通知は動きませんでした」と知らせる。会話の中のエージェントが書き換えたスクリプトを、その直後の
  書き込みで動かさないためである。Claude Code の側のコマンドには、この確かめを足さない（フックの定義のファイルそのものが
  作業ツリーの中にあり、同じ強さでは効かないため）。
- **`.claude/settings.json` の権限は、拒否の規則だけにする。** 規則は `Read(.env*)` と `Read(!.env.example)` の 2 つで、名前が
  `.env` で始まるファイルの読み取りを拒否し、`.env.example` を除く。許可の規則は置かない（`npm run <名前>` の許可は、
  `package.json` を書き換えれば任意のコマンドを確認なしで動かせる抜け道になるため）。`env` も置かない。
- **`check-docs.sh` に、検査する根を受け取る引数 `--root <絶対パス>` を足す。** 起動元の検査のスクリプトで、別の作業ツリーを
  検査するためである。引数なしの呼び出しは、これまでと同じに動く。

## 検討した代わりの案

- フックを置かず、検査は CI と手動だけにする: 危険は増えないが、文書の不備に気づくのが、`npm run check` か CI まで遅れる。
- Claude Code の側だけ、または Codex の側だけに置く: 片方のツールでは、早期通知が働かない。
- Bash の実行の後にも、作業ツリーの変更を調べて検査する: コマンドのたびに検査が動いて遅くなり、どの作業ツリーが
  変わったかを決められない。
- 早期通知で lint も動かす: 対象の設定と依存をプログラムとして読み込むので、対象のコードを実行することになる。
- Codex のコマンドを、会話の作業ディレクトリのある作業ツリーのスクリプトを実行する形にする: 本体で行ったフックの信頼が
  worktree の会話にも効く見込みなので、worktree に取り出した変更が書き換えたスクリプトが、信頼済みのフックから動く。
- スクリプトを、作業ツリーの外の、利用者の側の置き場へ写して動かす: リポジトリで共有できず、版のずれが生まれる。
- 拒否の規則を、名前の列挙（`.env`、`.env.local` など）で書く: 列挙に無い名前（`.env.staging` など）を止められない。

## 結果と限界

本物の会話で確かめたこと（マージの前の実機の確認。2026-10-13〜14。Claude Code 2.1.296 と codex-cli 0.162.1）:

実装した版で、本物の会話を 14 回（Codex 9 回、Claude Code 5 回）行い、14 回とも見込みのとおりだった。やり直した回は無い。
Codex の回は、対照の 1 回を除いて、フックの信頼の確認を、その回だけ省く引数を付けた。対照の 1 回は、この引数を付けずに行った。

- Codex:
  - 文書の検査が不合格になる書き込みの後に、不合格の文面がモデルに届く。
  - `docs` のサブディレクトリで始めた会話でも、早期通知が働く。
  - 1 回の書き込みが 2 つのパスを持つ場合（空白を含む名前を含む）も、両方を扱う。
  - 会話の作業ディレクトリと別の作業ツリーへ書くと、起動元は本体の作業ツリー、検査の対象は書いた側の作業ツリーになる。
    書いた側の作業ツリーに置いた、書き換えたスクリプトは実行されない。
  - worktree で始めた会話でも、本体の作業ツリーのスクリプトだけが動く。この回は、本体と worktree の両方の場所を、信頼する
    場所として起動の引数で渡した。
  - 本体の `scripts/harness/` の下にコミットしていない変更があると、スクリプトを動かさずに「早期通知は動きませんでした」と
    知らせ、その知らせがモデルに届く。
  - フックの信頼の確認を省く引数を付けない会話（対照の 1 回）では、信頼していないフックを実行しない。
  - Codex の会話からの `.git/config` への書き足しは、サンドボックスに拒否される。
- Claude Code:
  - Edit と Write のどちらの後にも、不合格の文面がモデルに届く。
  - `docs` のサブディレクトリで始めた会話では、フックが呼ばれない（下の、早期通知が働く範囲のとおり）。
  - 会話を始めた作業ツリーと別の作業ツリーへ書くと、起動元は会話を始めた作業ツリー、検査の対象は書いた側の作業ツリーになる。
    書いた側の作業ツリーに置いた、書き換えたスクリプトは実行されない。
  - 会話を始めた作業ツリーの `.env` の Read は拒否され、`.env.example` は読める。別の作業ツリーの `.env` は、絶対パスで
    Read すると読める（下の、拒否の規則の限界）。

フックの入力の形（Claude Code の `tool_input.file_path`、Codex の `tool_input.command` のパッチの見出し）が、上の版から変わると、
早期通知は「入力の形が、想定と違います」と知らせる。

早期通知が働く範囲と、使うときの決まり:

- Claude Code の早期通知は、作業ツリーの根で始めた会話でだけ働く。`.claude/settings.json` は、会話を始めたディレクトリから
  読まれるためである。サブディレクトリで始めた会話では、早期通知が出ず、同じファイルの拒否の規則も読まれない（`.env` が
  読める）。`/cd` で移った会話でも、同じになる見込みである（未確認）。会話の途中で、worktree に入る道具で worktree に入った
  場合は、会話を始めた側の定義とスクリプトが、そのまま使われる。
- Codex は、worktree で始めた会話でも、本体の作業ツリーの定義とスクリプトを使う。本体が `origin/main` より遅れていて、
  定義が無いと、知らせなしにフックが動かない。そのため、本体を `origin/main` に進めておく。
- Codex のフックは、`scripts/harness/` の下がコミットされた版から変わっていると、スクリプトを動かさずに「早期通知は
  動きませんでした」と知らせる。`scripts/harness/` の下を開発している間は、Codex の書き込みのたびに、この知らせが返る。
- Codex で、会話の作業ディレクトリと別の作業ツリーへ書くには、その作業ツリーを書き込める場所に足す指定（`--add-dir`）が要る。
- Codex のフックは、プロジェクトの信頼とは別に、フックの定義の信頼が要る。定義（`.codex/hooks.json`）を変えるたびに、
  利用者が対話の画面の `/hooks` で信頼し直す。し直すまで、知らせなしに飛ばされる。信頼は、取り出した場所ごとで、本体で
  行った信頼は worktree で始めた会話にも効き、別の clone では別に要る見込みである（実機では確かめていない。下の
  「そのほかの未確認の事項」）。信頼の対象は定義で、コマンドが呼ぶスクリプトの中身は対象にならず、`/hooks` の画面にも出ない。
- 起動元と対象でブランチが違うと、起動元の版の決まりで対象を検査するので、対象では正しい状態を不合格と知らせる
  ことがある。文面に、起動元の検査で確かめたことを書き、止めない。
- 早期通知には、次の上限がある。どれも、上限に達したら、黙って成功にせず、検査していないものがあることを知らせる。
  - 時間: 全体で 18 秒（フックの設定の `timeout` は 20 秒。設定の側が先に働くと、知らせを返せないので、短くしてある）。
    入力の変換、パスの判定の中の git の呼び出し、検査のどれも、残りの秒数を上限にして動かす。
  - 入力の大きさ: 8 MiB。超える入力は、読むのをやめて、書いたファイルを調べない。大きなファイルを 1 つ書いた入力も
    当たるので、文書でないファイルの書き込みでも、この知らせは出る。
  - 判定するパスの数: 1 回の書き込みにつき 200 件。数えるのは、名前が `.md` で終わるパスと、判定できないパス（空、改行を
    含むもの）だけで、名前が `.md` で終わらないパスは、いくつあっても数えず、知らせない。
  - 検査する作業ツリーの数: 1 回の通知につき 3 つ。

残る危険（承知のうえで置く）:

- フックは、サンドボックスと実行の確認の外で、利用者の権限で、作業ツリーの中のスクリプトを動かす。起動元そのものが
  信頼できない変更の作業ツリーである場合は、どちらのツールでも防げない。そのため、信頼できない変更の作業ツリーで会話を
  始めない。会話の途中で、そういう作業ツリーへ `/cd` で移らない（移った先の定義が読まれる見込みである）。Codex では、
  信頼できない変更を本体に取り出さない。
- Claude Code では、信頼できない変更を取り出した worktree で会話を始めると、その変更が書き換えた定義とスクリプトが動く。
  Claude Code を、対話の画面を使わない形（`-p`）で起動すると、信頼していないフォルダでも、プロジェクトのフックが承認なしで動く。
- 会話の中のエージェントが（誤って、または読み込んだ文書の指示に従って）3 つのスクリプトを書き換えると、Claude Code では、
  その直後の書き込みで、書き換えた版が動きうる。Codex の実行の前の確かめは、Codex をサンドボックスなしで使う場合、利用者が
  `.git` への書き込みを確認で許した場合、`PATH` に相対の項目がある場合には、破られうる。そのため、信頼できない文書を読ませる
  作業では、`HARNESS_NOTIFY=off` で早期通知を止める。`PATH` に相対の項目（`.` など）を入れない。
- Codex の実行の前の確かめが見るのは、`scripts/harness/` の下の、追跡されたファイルの変更である。同じ場所に足した、追跡
  されていない新しいファイルは見ない（3 つのスクリプトが、ほかのファイルを読み込んで実行しないことが前提である）。
- 追跡された中身に、git のディレクトリと、同じ内容のスクリプトを埋め込んだ場所で Codex の会話を始めると、実行の前の
  確かめを通る見込みである（未確認）。
- 変更がフックそのものを弱めたり、書き換えたりした場合は防げないので、次のものの変更は、人が差分を読んで確かめる
  （[0002](0002-secret-scan-scope.md) の一覧に加える）。
  - `scripts/harness/` の下のすべて（早期通知が実行する 3 つのスクリプトを含む）
  - `.claude/settings.json`（Claude Code のフックの定義と、拒否の規則）
  - `.codex/hooks.json`（Codex のフックの定義）

拒否の規則の限界（秘匿値を守る仕組みではない）:

- 効くのは Claude Code だけで、Codex には効かない。
- 誤って読むのを減らすだけである。スクリプト（`node` や Python など）が自分で開く読み取りと、規則に当たらない名前
  （`prod.env` など、`.env` で始まらない名前）は止まらない。
- Bash では、`cat`・`head`・`tail`・`sed`・`tee` とリダイレクト以外の命令に効くかは未確認である。
- 規則が読まれない会話がある。サブディレクトリで始めた会話と、`.claude/settings.json` を持たない古いブランチの worktree で
  始めた会話である。
- 止めるのは、名前が `.env` で始まるファイルのうち、会話を始めた作業ツリーの中のものだけである。別の作業ツリーの `.env` を、
  その作業ツリーに入らずに、絶対パスで読む場合は、止まらない（上の、本物の会話で確かめたこと）。会話の途中で worktree に
  入った後に、その worktree の中の `.env` に規則が効くかは、確かめていない（下の、未確認の事項）。
- 未確認の事項: 大文字と小文字を区別しないファイルシステムでの `.ENV`。シンボリックリンク経由の読み取り。Read 以外の
  道具（Grep など）が規則に従うか。除外の書き方（`!` で始まる規則）を知らない版の Claude Code での動作。会話の途中で
  worktree に入った後と、`/cd` で別の作業ツリーへ移った後に、規則が効くか。

そのほかの未確認の事項:

- Codex のフックの信頼の単位（上の、取り出した場所ごと、という見込み）。本物の会話で確かめた回は、本体と worktree の両方の
  場所を、信頼する場所として渡した。本体の場所だけを渡した場合に、worktree で始めた会話のフックが動くかは、確かめていない。
- 利用者が `/hooks` でフックを信頼した後の、フックの信頼の確認を省く引数を付けない、普段の使い方での動作（マージの後に
  確かめる）。
- VS Code の拡張では確かめていない。
- 対話の画面で、フォルダを信頼するときに、フックの中身が示されるかは確かめていない。親のフォルダを信頼済みの場合と、
  信頼済みのリポジトリの worktree で始めた会話では、信頼の確認なしにフックが動く見込みである。

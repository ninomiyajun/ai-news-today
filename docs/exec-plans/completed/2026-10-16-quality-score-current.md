# 品質目標に「現在の評価」の節と、目標の表の「検査の識別子」の列を足す

## 作業の場所

- ブランチ: `docs/quality-score-current`
- worktree のディレクトリ名: `wt-news-p8q`

## 目的

品質目標の文書（`docs/QUALITY_SCORE.md`）は、自分を P1（土台）の時点の仮置きとしていて、領域と層ごとの現在の評価を
持たない。目標の表の「確かめ方」の列も自由記述で、どの検査が目標を守っているかを機械的に読めない。次の 3 つを行う。

1. 冒頭の仮置きの文を外し、文書の役割（目標、測る項目、確かめ方と、現在の評価）を書く。
2. 目標の表に列「検査の識別子」を足す。識別子は `package.json` の `scripts` の名前そのもので、セルにはバッククォートで
   囲んだ識別子をコンマで区切って書く。人が確かめるだけの行は `-` と書く。後で入れる定期の走査が、この列を機械的に
   読んで、検査の結果と結び付けるためである。あわせて、技術的負債の一覧の TD-3 と TD-4 が指す 2 行を直す。
   - TD-3: 「外部と時刻を差し替えて試験できる」の測る項目に、通信のためのモジュールの使用を足す（`ARCHITECTURE.md` の
     不変条件 2 と `eslint.config.mjs`）。
   - TD-4: 「文書が実物と合っている」の測る項目を、文書の検査がいま確かめる範囲（`AGENTS.md` の検査のコマンドの表の、
     `npm run check:docs` の行）に合わせ、`test:harness` を足す。
3. 新しい節「## 現在の評価」を足す。評価の段階（A〜D）の定義、見直しの目安の 1 行、表 1「領域ごと」、表 2「層ごと」を置く。
   表の見出しの行の文字列は固定し、変えるときは走査の側も直す。

解消した TD-3 と TD-4 の行は、技術的負債の一覧の決まり（解消した変更で行を消す）のとおり、この変更で消す。

前提:

- 製品の仕様は無い（利用者に見える機能を変えない、文書の整備である）。
- 層、依存の向き、不変条件は変えない。`ARCHITECTURE.md` は読むだけで書き換えない。関係する ADR は
  `docs/adr/0001-layers-and-checks.md`（層と検査）。新しい ADR は書かない（設計判断を変えないため）。
- 品質目標の文書は、評価の作業場所に写される文書なので、製品の機能の名前や記事の取得の方式を、評価の文に書かない。
  同じ理由で、この文書から `docs/exec-plans/` と `docs/adr/` へのリンクを張らない（パスを文字で書く）。

決まっている書式:

- 評価の段階: `A`（目標を満たし、機械的な検査が守っている）、`B`（目標を満たすが、守りの一部が人の確認）、
  `C`（目標を一部満たさない、または確かめ方が無い）、`D`（目標を満たさない）。
- 見直しの目安の行: 「見直しの目安: 90 日」。
- 表 1 の見出しの行: `| 領域 | 評価 | 検査の識別子 | 根拠 | 評価した日 | 評価したコミット |`。行は目標の表の行と同じで、
  領域のセルは目標の表の「目標」のセルと同じ文字列。
- 表 2 の見出しの行: `| 層 | 評価 | 検査の識別子 | 人が確かめる決まりの数 | 根拠 | 評価した日 | 評価したコミット |`。
  行は `ARCHITECTURE.md` の 8 層と `templates/`。「人が確かめる決まりの数」は、`ARCHITECTURE.md` で「レビューで人が
  確かめる」とした決まりのうち、その層に当たる数。
- 評価した日は `YYYY-MM-DD` の形、評価したコミットは評価の根拠にしたコミット（短い形）。評価は、その時点の
  `npm run check` の段ごとの結果と `ARCHITECTURE.md` の記述から書き、利用者が確かめる。

## 発見

- `templates/module/` の試験のファイルは、`vitest.config.mts` の対象（`src/` の下の試験）の外にあり、`npm run test` で
  実行されない。ひな形の README に書いてあるとおりで、計画の前提と食い違うものではないが、`templates/` の評価の根拠に書いた。
- 評価したコミット `c4b6083` で、CI（ワークフロー `harness`）は成功していた（`gh run list` で確かめた）。CI は、push の
  たびに変更の範囲の各コミットの秘匿値の検査をするので、秘匿値の領域の評価の根拠にした。

## 判断の記録

1. 目標の表の見出しの行は `| 目標 | 測る項目 | 確かめ方 | 検査の識別子 |` とした。既存の 3 列を残し、末尾に列を足した。
   見出しの「目標（仮置き）」は「目標」にした。冒頭の仮置きの文を外すのと同じ理由である。
2. 表 2 の層のセルは、`ARCHITECTURE.md` の「依存の向き」の表と同じ形のパス（`src/app/` など）をバッククォートで囲んで書いた。
   層の名前（「画面」など）より、パスのほうが機械的に読むときに曖昧さが無いためである。
3. 「人が確かめる決まりの数」は、`ARCHITECTURE.md` で「レビューで人が確かめる」とした 4 つの決まりを、品質目標の文書の中に
   決まり 1〜4 として挙げ、対象にその層のファイルが入るものを数えた。決まり 1（`templates/` と `src/` の間の依存）は、
   どちらの向きの依存も対象なので、8 層と `templates/` のすべてに数えた。決まり 2 は `src/ports/` に当たらない（通信と
   現在時刻を使ってよい層のため）。その結果、`src/ports/` が 3、ほかが 4 になった。
4. 層の評価は、すべて `B` とした。どの層にも、ESLint や依存の検査が止められず人が確かめる決まりが 3〜4 つ当たり、段階の
   定義の「守りの一部が人の確認」に当たるためである。試験のファイルの無い実装のファイルがある層（`src/app/`、`src/ui/`、`src/sources/`、
   `src/ports/`、`src/domain/`）も、試験についての品質目標は `src/curation/` と `src/services/` だけが対象なので、`C` にしなかった。
5. 領域の評価は、人が確かめる決まりの当たる 2 つの領域（層の依存の向き、外部と時刻）と、記述の中身の照合を人に頼る文書の
   領域を `B`、機械的な検査だけで守る秘匿値と試験の領域を `A` とした。秘匿値の領域の `check:secrets:push` は `npm run check`
   に含まれず、この評価では実行していないが、CI が同じ検査をしていて評価したコミットの CI が成功したので `A` にした。
6. 目標の表の検査の識別子は、TD-4 の行にだけ `test:harness` を足した。`test:harness` は ESLint の規則と依存の規則の試験も
   含むが、それらの行は目標を守る検査そのもの（`lint`、`check:arch`）だけを書き、検査の試験の結果は評価の根拠に書いた。

# 保守の土台（技術的負債の一覧、検査の由来の記録、古い計画の検査、モジュールのひな形）を入れる

## 作業の場所

- ブランチ: `feat/harness-maintenance-base`
- worktree のディレクトリ名: `p7-maint-base`

## 目的

ハーネス（規約と検査の一式）を、作った後も保ち続けるための土台を入れる。次の 4 つである。

1. 技術的負債の一覧（`docs/exec-plans/tech-debt-tracker.md`）。作業の範囲外で見つけた問題を、その場で直さずに書き留める場所が
   無く、完了した計画の「結果と振り返り」に散らばっているためである。
2. 検査の由来の記録（`docs/harness-log.md`）。指摘から作った検査が、どの指摘から生まれ、文書のどの記述を置き換えたかを
   残す場所が無いためである。この変更では表の見出しだけを置き、行は、指摘を検査にする変更が足す。
3. 古い計画の検査（`npm run check:docs` の検査 11）。進行中の計画が、進められないまま `docs/exec-plans/active/` に残り続けても、
   気づく仕組みが無いためである。30 日以上、日付の更新が無い進行中の計画を失敗にする。
4. モジュールのひな形（`templates/module/`）。新しいモジュールを足すときの、実装と試験の 1 組の出発点である。

前提:

- 製品の仕様は無い（利用者に見える機能を変えない、内部の整備である）。
- 層、依存の向き、不変条件は変えない。モジュールのひな形は `src/` の外（`templates/`）に置くので、
  `npm run check:arch`（`src/` の直下の名前と、層の依存の向き）の対象にならない。`ARCHITECTURE.md` には、「層と責務」の節に、
  `templates/` が層でないことと、ひな形が `src/` の何も import しない決まりだけを足す（判断の記録の 7）。
- 関係する ADR は `docs/adr/0001-layers-and-checks.md`（層と検査）である。新しい ADR は書かない（層、依存の向き、
  不変条件を変えないため）。
- 依存（`package.json` と `package-lock.json`）は変えない。検査 11 は、いまある道具（bash、awk、sed、grep）だけで書く。

決まっている仕様（検査 11）:

- 対象は、`docs/exec-plans/active/` の直下の計画（名前が `.acceptance.md` で終わらない `.md`）。`completed/` の計画と、
  受け入れ確認の記録は対象にしない。
- ファイル名の先頭の日付と、「進捗」の節の中の `YYYY-MM-DD` の形の日付（コードブロックの中は数えない）のうち、最も新しい日付が、
  基準の日より 30 日以上前なら失敗にする。基準の日の 1 日後より後の日付は数えない（判断の記録の 8）。暦に無い日付と、
  前後に数字が続く並びも数えない（判断の記録の 6）。数える日付が 1 つも無い計画は、古さを判定できないとして失敗にする。
- 基準の日は、環境変数 `HARNESS_TODAY`（`YYYY-MM-DD`。試験用）があればその日、無ければ実行した日。日数は、スクリプトの
  冒頭の変数 `STALE_PLAN_DAYS=30` に持つ。
- 失敗の表示には、計画のパス、最も新しい日付、経過の日数と、直し方（進めたなら進捗の節に日付の行を足す。終えたなら結果を
  書いて `completed/` へ移す。やめたなら、やめた理由を結果に書いて `completed/` へ移す）を出す。

## 発見

1. **試験の見本の計画の進捗の節に日付が無いと、基準の日を渡すだけでは、試験が基準の日に左右される。** 既存の試験は、
   `docs/PLANS.md` の「新しい書式の適用開始」の日付をファイル名に持つ計画を `active/` に置いて、通ることを期待する場合を持つ。
   基準の日の既定を適用開始の日に固定すれば通るが、既定を 40 日後に替えると、それらの計画が検査 11 で古い計画になり、
   通るはずの場合が失敗に変わる。そこで、見本の計画を書く関数が、進捗の節に、基準の日の既定の日付の行を書くようにした
   （判断の記録の 2）。
2. **`templates/` の下の `.tsx` は、`npm run typecheck` と `npm run lint` の対象になり、`npm run test` の対象にならない。**
   `tsconfig.json` の `include` が `**/*.tsx` で、`vitest.config.mts` の `include` が `src/` の下だけのためである。
   ひな形の試験が `@/ui/...` の形で実装を import すると、その先のファイルが無いので型の検査が失敗する（判断の記録の 3）。
3. **進捗の節の日付をすべて数えると、先の日付が 1 つあるだけで、検査 11 が古い計画と判定しなくなる。** はじめの実装で、
   この計画の進捗の節に、V4 で基準の日にした 40 日後の日付を書いたところ、V4 の操作が終了コード 0 で通った。進捗の節には
   「残っている手順」も書くので、再開の予定の日付も入りうる。そこで、基準の日の 1 日後より後の日付を数えないように検査を
   直した（判断の記録の 8）。基準の日の 1 日後までの日付は、作業をした日でなくても数えるので、進捗の節に、作業をして
   いない日の日付を書かないことは、検査では防げない。直した後も、この計画の進捗の節に V4 の基準の日そのものを書くと、
   その日付が数えられて V4 の操作が通る（確かめた）。そのため、進捗の節には、その日付を書いていない。

## 判断の記録

1. **日数の計算は awk で行う。** `date` コマンドの日付の計算は、macOS と Linux で書き方が違い、手元と CI で同じスクリプトを
   使えないためである。日付を通しの日数に直して引く。
2. **試験の見本の計画には、進捗の節に、基準の日の既定の日付の行を書く。** 発見の 1 のとおり、検査 11 の対象でない場合の結果を、
   基準の日に左右させないためである。検査 11 の場合は、進捗の節の中身と基準の日を、場合ごとに自分で指定する。試験の基準の日の
   既定を替える環境変数の名前は `HARNESS_TEST_TODAY` とした。
3. **ひな形の試験は、実装を相対のパス（`./ExampleLabel`）で import する。** 発見の 2 のとおり、`@/` の形では型の検査が通らない
   ためである。`src/` の下へ写した後に、既存の試験と同じ `@/<層の名前>/<ファイルの名前>` の形に直すことを、ひな形の README と
   試験のコメントに書いた。ファイルの拡張子を変えて検査の対象から外す案は採らなかった。型の検査と lint の対象にしておくと、
   依存の版が上がったときに、ひな形が古くなったことに気づけるためである。
4. **検査 11 の試験は、起票の時点で決めていた 8 つの場合に、後から足して 25 件にした。** はじめに足したのは、名前が日付で
   始まらないが進捗に新しい日付がある、進捗の節の外に書いた日付は数えない、直し方の文言が出る、基準の日が日付の形でない、
   の 4 つである。レビューの指摘を受けて、基準の日の 1 日後と 2 日後の日付、1 日後より後の日付しか無い計画、ちょうど 30 日と
   29 日の境界（年をまたぐ場合と、うるう年の 2 月をまたぐ場合）、暦に無い日付（平年の 2 月 29 日、4 月 31 日）、うるう年の
   2 月 29 日、前後に数字が続く並び、進捗より後の節の日付、日付が無いときの直し方の文面を足した。どれも、決まっている
   仕様の範囲の中の振る舞いを確かめるものである。
5. **`HARNESS_TODAY` が、`YYYY-MM-DD` の形の、暦にある日付でないときは、失敗にする。** 形の崩れた値や、暦に無い日付
   （平年の 2 月 29 日など）を黙って受け入れると、基準の日を指定したつもりの確認が、別の日の扱いで行われるためである。
6. **日付として数えるのは、暦にある日付だけにする。前か後ろに数字が続く並びは、日付として取り出さない。** はじめは、月が
   01〜12、日が 01〜31 であることだけを確かめ、月ごとの日数は見ていなかった。2 段目のレビューの指摘で、月ごとの日数と
   うるう年の 2 月を確かめる関数を置き、基準の日と、計画から取り出した日付の両方に使う形に直した。あわせて、長い数字の一部
   （`12026-10-07` の中の `2026-10-07` など）を日付と読まないように、取り出すときに前後の文字が数字でないことを確かめる。
   どちらも、日付でない数字の並びを、新しい日付と読み違えないためである。

7. **`ARCHITECTURE.md` の「層と責務」の節に、`templates/` の位置づけの段落を足した（起票の時点の前提「`ARCHITECTURE.md` は
   変えない」を変えた）。** 設計の正本は「コードはすべて `src/` の下に置く」と書いているのに、この変更は `src/` の外に実装と
   試験のファイルを置く。ひな形が `src/` の何も import しない決まりも、どこにも書かれていなかった。ひな形を直す人が
   `src/` のものを import しても `npm run check` は通るので、決まりを設計の正本に書いて、コードを変える前に読まれるようにした。
   同じ決まりを、ひな形の README にも書いた。層、依存の向き、不変条件は変えていない。V6 も、この変更に合わせて直した。
   `AGENTS.md` の文書の地図には、ひな形を載せない（地図は文書の種類で引く表で、ひな形は設計の正本から辿れるため）。
8. **基準の日の 1 日後より後の日付は、最も新しい日付の候補から外す。** 発見の 3 のとおり、予定の日付を、進めた日付と読み違え
   ないためである。1 日後までは数える。手元と CI では時刻帯が違い、「実行した日」が 1 日ずれうるためである。ファイル名の
   日付も同じ扱いにする。外した結果、数える日付が 1 つも無くなった計画は、日付を 1 つも読めない計画と同じく、古さを判定
   できないとして失敗にする（ファイル名の日付だけを特別に残す分岐は作らない）。
9. **技術的負債の一覧と、検査の由来の記録の書式を、次のように決めた。** (a) 技術的負債の識別子は使い回さず、次に使う識別子を
   表の前の 1 行に持って、行を足す変更で進める。解消した行は消す決まりなので、表だけからは、使った数字が分からなくなるため
   である。(b) 検査の由来の記録は、検査を外しても行を消さず、「外した変更」の列を埋める。外した理由を残すためである。
   (c) どちらの文書でも、計画はファイル名だけで書き、ディレクトリを付けない。計画を閉じると置き場が変わるためである。
10. **`eslint.config.mjs` は、この変更では変えない。** ひな形には、`src/` の下と同じ ESLint の規則（不変条件 1、2、5）が
    かからず、`src/` を import しない決まりを守らせる検査も無い。この 2 点は、技術的負債の一覧に TD-1 と TD-2 として書いた
    （判断の記録の 13）。
11. **日付を扱う awk の関数は、どの awk でも同じ結果になるように、`substr`、`int`、四則と剰余だけで書く。** 手元（macOS）と CI（Linux）で awk の
    実装が違うためである。年をまたぐ場合と、うるう年の 2 月をまたぐ場合を、試験に足した。

12. **検査 7（`ARCHITECTURE.md` に書いたパスの実在）の対象に、`templates/` で始まるパスを足した。** 判断の記録の 7 で
    `ARCHITECTURE.md` に `templates/module/` を書いたが、検査 7 が見るのは `src/`、`docs/`、`scripts/`、`.github/` で始まるパスと
    根のファイル名だけで、足した記述のパスが消えても気づけなかったためである。足した後も、いまの `ARCHITECTURE.md` で
    新しく失敗になる記述は無い（`npm run check:docs` が通る）。

13. **技術的負債の一覧の最初の行は、この作業で見つけた 2 件（TD-1、TD-2）にした。** 候補は 3 件あり、どれを書くかは利用者が
    決めた。書かなかった 1 件は、完了した計画の「結果と振り返り」に、範囲外として残したことが既に書かれている。

## 結果と振り返り

結果:

- 技術的負債の一覧（`docs/exec-plans/tech-debt-tracker.md`）、検査の由来の記録（`docs/harness-log.md`）、古い計画の検査
  （`npm run check:docs` の検査 11）、モジュールのひな形（`templates/module/`）を入れた。`AGENTS.md` の文書の地図に 2 つの文書を

- 基準 V1〜V6 はすべて合格した。`npm run check` は終了コード 0 で、`npm run test:harness` は「115 件中 115 件が期待どおり」
  だった（この変更の前は 88 件）。計画を閉じた後の V5 も、終了コード 0 だった。
- 依存（`package.json`、`package-lock.json`）、`eslint.config.mjs`、CI の設定、`scripts/harness/check-arch.sh` は変えていない。
- 新しい ADR は書いていない。層、依存の向き、不変条件を変えず、判断はこの計画の判断の記録で足りるためである。

レビューで直したこと:

- 1 段目（設計品質のレビューと実装レビュー）: ひな形の位置づけと、`src/` の何も import しない決まりを `ARCHITECTURE.md` に
  書いた。進捗の節の先の日付を数えないようにした。技術的負債の識別子を使い回さない決まりと「次に使う識別子」の行、検査の
  由来の記録の「外した変更」の列を足した。出どころは、計画のファイル名だけで書くことにした。

  計画の日付としても受け入れないようにした。長い数字の一部を、日付として取り出さないようにした。

振り返り:

- 日付を見る検査は、試験を実行した日で結果が変わりうる。検査を呼ぶ箇所を 1 つにまとめ、そこで必ず基準の日を渡す形にすると、
  渡し忘れを検索で確かめられる。見本の計画の側にも、基準の日に合わせた日付を書いておく必要があった（発見の 1）。
- 「進捗の節の日付をすべて数える」という単純な決まりは、予定の日付、暦に無い日付、日付でない数字の並びの 3 つで、意図と
  違う結果になった。どれもレビューと、この計画そのものを検査にかけたことで見つかった（発見の 3）。
- 設計の正本に決まりを足したら、その決まりが書いたパスを検査が見ているかも、同じ変更で確かめる（判断の記録の 12）。

確かめていないこと:

- 日付を扱う awk の関数は、手元（macOS の awk）でだけ実行した。CI（Linux）の awk での実行は、この変更の PR の CI で、
  `npm run test:harness` が通ることで確かめる。関数は、どの awk にもある書き方だけで書いてある（判断の記録の 11）。

範囲外として残したこと（技術的負債の一覧に書いた）:

- TD-1: ひな形に、`src/` の下と同じ lint の規則がかからない。
- TD-2: ひな形が `src/` の何も import しない決まりを、守らせる検査が無い。

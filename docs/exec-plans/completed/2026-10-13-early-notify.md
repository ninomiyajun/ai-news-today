# 早期通知（ファイルを書いた直後に、フックから文書の検査を動かして知らせる）を入れる

## 作業の場所

- ブランチ: `docs/early-notify-verified`
- worktree のディレクトリ名: `news-p7-notify-docs`

実装（手順 1〜7、手順 9 の実装レビューの 2 段目、手順 10）は、ブランチ `feat/early-notify`、worktree `news-p7-notify` で行い、
pull request #28 でマージした。上の 2 つは、その後に、実機の確認の結果を書いてこの計画を閉じた場所である（判断の記録の 20）。

## 目的

Claude Code と Codex がファイルを書いた直後に、書いたファイルのある作業ツリーの文書の検査（`npm run check:docs` と同じ
`scripts/harness/check-docs.sh`）を動かし、不合格をエージェントに知らせる仕組み（早期通知）を入れる。文書の不備に、
`npm run check` や CI まで待たずに気づけるようにするためである。知らせるだけで、作業は止めない。止めるのは、これまでと
同じく `npm run check` と CI である。

入れるものは次の 4 つである。

1. 早期通知の入口 `scripts/harness/notify.sh` と、フックの入力から書いたファイルのパスを取り出す
   `scripts/harness/notify-paths.mjs`、その試験 `scripts/harness/notify.test.sh`。
2. `scripts/harness/check-docs.sh` の引数 `--root <絶対パス>`（起動元の検査のスクリプトで、別の作業ツリーを検査するため）。
3. Claude Code のフックの設定と拒否の規則（`.claude/settings.json`）と、Codex のフックの設定（`.codex/hooks.json`）。
4. `AGENTS.md` の検査の表の 1 行と、落とし穴。判断の理由と限界は、ADR `docs/adr/0005-early-notify-hooks.md` に書く。

前提:

- 製品の仕様は無い（利用者に見える機能を変えない、内部の整備である）。
- `ARCHITECTURE.md` の層、依存の向き、不変条件は変えない。変えるのは `src/` の外（`scripts/harness/`、`.claude/`、`.codex/`）だけ
  である。関係する ADR は `docs/adr/0001-layers-and-checks.md`（層と検査）と `docs/adr/0002-secret-scan-scope.md`（秘匿値の検査の
  範囲）で、どちらも変えない。
- 依存（`package.json` の `dependencies` と `devDependencies`、`package-lock.json`）は変えない。早期通知は、bash、node の
  組み込みのモジュール、perl、git だけで書く。

決まっている設計（この計画の外で、設計レビューとセキュリティレビューを通したもの。ここには、実装と再開に要る点を書く）:

- 用語: 「起動元」は、フックの定義と、実行される `notify.sh` のある作業ツリー。Claude Code では会話を始めた作業ツリー、
  Codex では本体の作業ツリーである（Codex は、worktree で始めた会話でも、フックの定義を本体の側から読むため）。「対象」は、
  書いたファイルのある作業ツリー。
- 安全の原則: 早期通知が実行するプログラムは、起動元にあるものだけにする。対象にある実行できるファイル（検査の
  スクリプト、設定のプログラム、依存のパッケージ）を、起動も読み込みもしない。対象は、検査される文書としてだけ読む。
  同じリポジトリの別のブランチが書き換えたスクリプトを、利用者の権限で動かさないためである。そのため、動かす検査は
  文書の検査だけにし、lint・型・試験は動かさない（ESLint は、対象の設定と依存をプログラムとして読み込むため）。
- 実行するものは、`notify.sh`、`notify-paths.mjs`、`check-docs.sh` の 3 つに限る。3 つは、ほかのファイルを読み込んで
  実行せず、`notify-paths.mjs` は `node:` で始まる組み込みのモジュールだけを読み込む。Codex のフックのコマンドが、実行の
  前に、この 3 つがコミットされた版から変わっていないことを確かめるので、3 つのほかに実行されるファイルがあると、
  その確かめの外になる。
- 対象にする書き込みは、Claude Code の Edit・Write と、Codex の `apply_patch` だけである。Bash による書き込みは拾わない。
- `notify.sh` の流れ: (1) 環境変数 `HARNESS_NOTIFY=off` なら何もしない。(2) 起動元の根を、自分の置き場から決める（作業
  ディレクトリに頼らない）。(3) 入力の変換で、書いたファイルの絶対パスの一覧を得る。Codex のパッチの見出しは
  `*** Add File: `、`*** Update File: `、`*** Delete File: `、`*** Move to: ` の 4 種類を受け、相対パスは入力の `cwd` を基準に
  する。(4) パスごとに、空・改行を含む・名前が `.md` で終わらない・親ディレクトリが無い・シンボリックリンク・git の
  作業ツリーの外・起動元と git の共通のディレクトリが違う、のどれかなら対象外にする（`.md` で終わるかを見るまでは git を
  呼ばない）。(5) 対象の根ごとに 1 回だけ、`/bin/bash <起動元の根>/scripts/harness/check-docs.sh --root <対象の根>` を動かす。
  1 回の通知で検査する根は 3 つまで。(6) 時間の上限は、全体で 18 秒（フックの設定の `timeout` は 20 秒）。(7) 不合格・
  時間切れ・入力の形の変化・起動の失敗のときだけ、標準出力へ JSON（`hookSpecificOutput` の `additionalContext`）を出す。
  文面は 2000 字までで、根は、ディレクトリの名前だけを出す。(8) 終了コードは、どの場合も 0。(9) リポジトリの中には何も
  書かない。環境変数 `HARNESS_NOTIFY_LOG` があるときだけ、そのファイルに 1 行を足す。
- `check-docs.sh --root`: 値が、絶対パスでない、ディレクトリでない、git の作業ツリーの根でないときは、検査せずに終了コード 2。
  引数なしの呼び出しは、これまでと同じに動く。検査の中身（1〜11）は変えない。
- `.claude/settings.json`: `PostToolUse`、`matcher` は `Edit|Write`、コマンドは
  `/bin/bash "$CLAUDE_PROJECT_DIR"/scripts/harness/notify.sh claude`、`timeout` は 20。権限は、拒否の規則 `Read(.env*)` と
  `Read(!.env.example)` の 2 つだけを、この順に置く。許可の規則と `env` は置かない。
- `.codex/hooks.json`: `PostToolUse`、`matcher` は `apply_patch`、`timeout` は 20。コマンドは、本体の作業ツリーの、
  コミットされた版から変わっていない 3 つのスクリプトだけを実行する 1 行で、文面は設計で確定している（1 字でも変えると、
  利用者がフックを信頼し直すまで、Codex はフックを飛ばす）。`.codex/config.toml` は置かない（要る設定が無いため）。

この計画の範囲は、マージの前の実装と、マージの前の実機の確認までである。マージの後の確認（利用者が Codex の対話の画面で
フックを信頼した後の、普段の使い方での確認）は、マージの後にしか行えないので、この計画に入れない。

## 発見

- 追跡された中身に埋め込まれた git のディレクトリが、設定（`core.worktree`）で作業ツリーを同じリポジトリの worktree に
  向けていると、その中のファイルから求めた作業ツリーの根が、その worktree になる。根から git の共通のディレクトリを
  求め直すと、起動元と同じになり、対象外にならなかった（実行されるのは起動元の検査だけなので、プログラムが実行される
  経路ではないが、書いていない作業ツリーを検査する）。共通のディレクトリを、根からではなく、根を求めたのと同じ親
  ディレクトリから求める形にし、親ディレクトリが根の下に無いものも対象外にした。試験 5 に、この場合を足した。
- 時間の上限の実装は、perl が子のプロセスを作り、子の側を新しいプロセスグループにして、時間が来たら、そのグループへ
  終了の信号を送る形にした。perl 自身をグループに入れる形では、終了の信号が perl 自身にも届き、決めた終了コード（142）を
  返せないことがあるためである。
- `AGENTS.md` は、落とし穴を 18 行で足すと 119 行になった（上限は 120 行）。実装レビューの指摘で、内訳と未確認の事項を
  ADR 0005 へ移し、落とし穴を 8 行にして、109 行にした（判断の記録の 13）。
- 時間の上限の値（`HARNESS_NOTIFY_TIME_LIMIT`）が `08` や `09` だと、算術の式で 8 進数の誤りになり、上限が働かなくなって
  いた（実装レビューの指摘）。先頭が 0 の値を受けない形に直した。

## 判断の記録

1. ログ（`HARNESS_NOTIFY_LOG`）の行に、設計が挙げた項目（時刻、呼び出し元、起動元の根、検査した根、対象外にしたパスの数と
   理由、結果）に加えて、対象にした文書のパス（`files`）を入れた。マージの前の実機の確認で、1 回のパッチの 2 つのパスが
   渡ったことを、ログで確かめるためである。
2. 入力の変換（`notify-paths.mjs`）は、判定できないパス（空、NUL や改行を含む）を、絶対パスの代わりに、`!` で始まる目印で
   出す。出力が NUL 区切りなので、そのままでは、対象外にした数と理由を `notify.sh` へ渡せないためである。
3. 相対パスは、入力の `cwd` と文字列としてつなぎ、`..` を畳まない。シンボリックリンクを挟むと、畳んだ結果が実際の場所と
   ずれるためである。実体のパスへの解決は、`notify.sh` が、親ディレクトリへ移って行う。
4. 時間の上限は、試験のために、環境変数 `HARNESS_NOTIFY_TIME_LIMIT`（1〜18 の整数）で短くできる。長くはできない
   （フックの設定の `timeout` の 20 秒を超えると、知らせを返せないため）。
5. 検査が、不合格（終了コード 1）でも時間切れでもない終了コードで終わったときは、「検査を実行できませんでした」と
   知らせる（設計が挙げた「起動の失敗」に含めた）。
6. 試験 11（時間切れ）の上限は 5 秒にした。1 秒では、検査を始める前の処理が、混んだ機械で 1 秒を超えて、検査を
   始める前に時間切れになることがあったためである。
7. 試験 17 の `/bin/zsh` での確かめは、zsh が無い環境（CI の Ubuntu など）では省き、省いたことを出力に出す。`/bin/sh` での
   確かめは、どの環境でも行う。zsh の設定は、利用者の設定を読まないように、環境変数 `ZDOTDIR` で空の見本に向ける。
8. `AGENTS.md` の落とし穴は、設計が挙げた項目を、6 つの箇条にまとめた（上限 120 行に収めるため）。会話の途中で worktree に
   入った後に拒否の規則が続くことは、マージの前の実機の確認（V6）の結果を見てから書くと決まっているので、書いていない。
9. パスの判定のループに、時間の上限と、パスの数の上限（200 件）を足した（実装レビューの指摘）。多数のパスを持つ入力で、
   判定だけで時間を使い切り、フックの設定の `timeout` で打ち切られて、知らせを返せなくなるのを防ぐためである。上限に
   達したら、残りを判定せずに、判定していないパスがあることを知らせる。200 件は、1 回のパッチが書く文書の数として
   十分に大きく、文書でないパス（git を呼ばない）だけなら 1 秒かからずに判定できる数として決めた。
10. 時間の上限の値は、先頭が 0 でない 1〜2 桁の整数だけを受ける。上限つきで動かす関数は、秒数が 1 以上の整数でなければ、
    動かさずに時間切れと同じ終了コードを返す（上限の無い実行をしないため）。
11. 検査が、不合格でも時間切れでもない終了コードで終わったときは、検査の出力を文面に入れない（シェルの誤りの表示などに、
    起動元の絶対パスが入りうるため）。判断の記録の 5 の文面は、終了コードだけを知らせる形になった。
12. 冒頭で、環境変数 `CDPATH` を外す（`cd` が、別のディレクトリへ移らないようにするため）。ログの、対象外の理由ごとの数は、
    実際に記録した理由の語から数える形にした（理由の名前の一覧を 2 か所に持たないため）。
13. 公開リポジトリにフックを置く判断、起動元と対象の分離、動かす検査を文書だけにした理由、Codex の実行の前の確かめ、
    残る危険と未確認の事項を、ADR `docs/adr/0005-early-notify-hooks.md` に書いた（起票の時点では、ADR を書かないとして
    いた）。`AGENTS.md` の落とし穴は、行動を変える要点と ADR への参照だけにした。
14. 後で行うこと: `.github/workflows/harness.yml` の段の名前「test-harness（文書の検査の試験）」は、早期通知の試験も動かす
    ようになったので、実態と合わない。この変更では CI の設定を変えないと決めているので直さず、CI の設定を変える次の
    変更で直す。
15. パスの判定の中の git の呼び出しにも、残りの秒数の上限をかけた（実装レビューの 2 段目の指摘）。判定の開始の前にだけ
    残りの時間を見る形では、最後の 1 件の git が長引くと、全体の上限を超え、時間切れの知らせも付かなかったためである。
    git が時間切れで終わったら、残りを判定せずに、判定していないパスがあると知らせる。あわせて、直前と同じ親ディレクトリの
    パスは、前の結果を使う形にした（同じディレクトリの文書を多く書いたときに、git を呼び直さないため）。
16. フックの入力の大きさに、上限（8 MiB）を足した（同じ指摘）。超えたら、読むのをやめて、「入力が大きすぎて、調べて
    いない」と知らせる。8 MiB は、文書やコードを書く 1 回の入力として十分に大きく、メモリーに読み込んでも負担にならない
    値として決めた。大きなファイルを 1 つ書いた入力も当たるので、この場合に限り、文書でない書き込みでも知らせが出る
    （入力を読み切らないと、文書かどうかを決められないため）。
17. 名前が `.md` で終わらないパスは、入力の変換（`notify-paths.mjs`）が、数だけを数えて捨てる形にした（再確認の指摘）。
    パスの数の上限（200 件）は、名前が `.md` で終わるパスと、判定できないパスだけを数える。判断の記録の 9 の形では、
    文書でないファイルを 201 個以上書くと知らせが出て、「文書でない書き込みでは何も出さない」決まりから外れていた。
    入力の変換も、出すパスを 200 件までにし、超えたら目印を 1 件出す。`notify.sh` は、上限に達したら、残りを読まずに終える。
18. 試験 11 の、全体の時間切れの確かめと、子と孫のプロセスが残らないことの確かめを分けた（実装レビューの 2 段目の指摘）。
    前者は、短くした上限（5 秒）で、どの段階の時間切れかを問わずに確かめる。後者は、既定の上限（18 秒）の回で、検査の
    見本が PID を書き終えたことを確かめてから確かめる。短くした上限では、混んだ機械で、検査が起動する前に時間切れに
    なり、実装が正しくても試験が落ちうるためである。試験は、標準入力をファイルから渡す形にした（早期通知が、大きすぎる
    入力を途中で読むのをやめても、渡す側の書き込みの失敗にしないため）。
19. `AGENTS.md` の落とし穴の、止め方の文に、使う場面（信頼できない文書を読ませる作業）を足した（再確認の指摘）。ADR 0005 に、
    上限の値と、上限で知らせる場合を書いた。
20. 手順 9 の「結果を書いて、この計画を閉じる」を、pull request #28 のマージの後に、別の pull request で行った。実機の確認
    （手順 8）の結果は、マージの前に pull request #28 に足す予定だったが、pull request #28 は、足す前の内容でマージされたため
    である。スクリプトとフックの定義は、実機の確認で使った版のまま変えていないので、実機の確認はやり直していない。
    「作業の場所」の節は、計画を閉じた時点のブランチと worktree に直し、実装を行った場所を、その下に残した。
21. 実機の確認の結果を受けて、`AGENTS.md` の落とし穴の、拒否の規則の箇条に、止める範囲（会話を始めた作業ツリーの中の、
    `.env` で始まる名前だけ）を足した。別の作業ツリーの `.env` を絶対パスで読むと読めたためである。規則の形を変えて止める
    ことは、しなかった（拒否の規則は、秘匿値を守る仕組みではない、という位置づけを変えないため）。会話の途中で worktree に
    入った後に拒否の規則が続くか（判断の記録の 8）は、実機の確認で確かめなかったので、落とし穴に書かず、ADR 0005 の未確認の
    事項に残した。

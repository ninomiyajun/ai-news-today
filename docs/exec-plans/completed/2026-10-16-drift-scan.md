# 定期の走査（drift-scan）を入れる

## 作業の場所

- ブランチ: `feat/drift-scan`
- worktree のディレクトリ名: `wt-news-p8s`

## 目的

文書の点検は、利用者が依頼したときにしか動かない。時間が経つだけで起きるずれ（古くなった計画、解消したのに残る
技術的負債の行、古い品質の評価、実行の環境の変化）は、依頼の間に拾えない。そこで、毎週の CI の予定実行で走査し、
ずれの材料を報告 `report.md` にまとめて、公開してよいことを確かめたうえで CI の成果物に残す。結果は通知せず、
所見があってもジョブを失敗にしない。報告は、後で文書の点検の担当が読む材料になる。

行うこと:

1. 走査の本体 `scripts/harness/drift-scan.sh`（新規）。引数は `--out <置き場>`。項目 1〜5（下の「走査の項目」）を行い、
   `report.md` だけを書く。書いた後に公開してよいかの検査を行い、通らなければ報告を消して終了コード 3。所見があっても
   終了コード 0。走査を続けられないとき（引数の誤り、git の履歴が無い、`package.json` を読めないなど）は 2。
2. 走査の試験 `scripts/harness/drift-scan.test.sh`（新規）。一時ディレクトリに見本のリポジトリを作って走査を呼ぶ。
   `npm run test:harness` の最後に足す。
3. ワークフロー `.github/workflows/drift-scan.yml`（新規）。毎週月曜 00:23 UTC の予定実行、手動の実行、走査と走査が読む
   文書を変える PR で動く。権限は `contents: read`。走査が通ったときだけ、報告を成果物 `drift-scan-<実行の番号>` として
   上げる（保存期間は予定実行で 90 日、ほかは 7 日）。冒頭の注釈に「# 間隔の日数: 7」と「# 成果物の名前の接頭辞: drift-scan-」を書く。
4. `package.json` に `scan:drift` を足し、`test:harness` の最後に走査の試験を足す。`check` は変えない（走査は検査ではないため）。
5. `AGENTS.md` の文書の地図に「定期の走査」の行、検査のコマンドの表に走査の行、検査の試験の行の説明に「定期の走査」、
   落とし穴に予定実行が 60 日で止まることの行を足す。
6. `.github/workflows/harness.yml` の段の名前「test-harness（文書の検査の試験）」を、`test:harness` の範囲に合わせる。
   解消した技術的負債 TD-5 の行を `docs/exec-plans/tech-debt-tracker.md` から消す。
7. 判断の記録 `docs/adr/0006-drift-scan.md`（新規）と、`docs/adr/README.md` の目録の行。

走査の項目（報告の各行に、行の識別子を付ける。判定は件数でなく、要対応の行の識別子の集合で行う）:

| 項目 | 行の識別子 | 何をするか | 要対応にする条件 |
|---|---|---|---|
| 1 検査の一式 | `1/<段>` | `package.json` の `check` に並ぶ段を読み、段ごとに別々に実行し、失敗しても続ける。終了コードと所要秒だけを書く。`check:docs` は `HARNESS_TODAY` を付けずに実行する | 終了コードが 0 でない段 |
| 2 文書の鮮度 | `2/<文書のパス>` | 文書の地図のファイルごとに、最後の変更の日、文書が書く実在のパス（検査 7 と同じ形）の数、その後にそれらのパスを変えたコミットの数 | なし（参考） |
| 3 技術的負債の一覧 | `3/<TD-n>` | 場所のパス、見つけた日からの日数、場所のファイルの有無、見つけた日より後に場所のファイルを変えたコミットの数 | 場所のファイルが無い行 |
| 4 品質目標の評価 | `4/領域:<領域>`、`4/層:<層>`、`4/表` | 「現在の評価」の行ごとに、評価した日からの日数と、検査の識別子ごとの項目 1 の結果（`check` に無い識別子は「照合しない」） | 見直しの目安の日数を超えた行、評価が `A` か `B` なのに識別子の段が失敗した行、表の書式に合わない行があるとき（`4/表`） |
| 5 実行の情報 | `5/<項目>` | 契機（CI の外では `local`）、日時（UTC）、対象のコミット、間隔の日数（ワークフローの注釈から）、保存期間、`origin/main` の最後のコミットからの日数、試験の差し替えの有無 | `origin/main` の最後のコミットから 45 日以上、試験の差し替えが「あり」 |

報告の 1 行めは「走査の結果: 要対応 <n> 件」、次に項目 5、続けて項目 1〜4 の表、最後に書式の説明。報告に書くのは、
識別子、リポジトリの根からの相対のパス、日付、日数、数、終了コード、印（要対応、参考、照合しない）だけで、コミットの
作者、コマンドの出力、文書の本文の抜粋、環境変数の値は書かない。公開してよいかの検査は、置き場に `report.md` 以外の
ファイルが無いこと、絶対パスの形（`/home/`、`/Users/`、`/tmp/`、`/private/`、`/var/`、`/opt/`、`/runner/` と、
`GITHUB_WORKSPACE`・`RUNNER_TEMP` の値）、メールアドレスの形、secretlint の規則（`.secretlintrc.json`）に当たる値が無いことを確かめる。

品質目標の表の読み方（`docs/QUALITY_SCORE.md` の冒頭の決まり）: 目標の表と「現在の評価」の 2 つの表は、見出しの行の
文字列と列の数が決まっている。セルは前後の空白を除き、検査の識別子は、コンマで区切った各要素のバッククォートを外した
文字列として読み、`package.json` の `scripts` にあることを確かめる。

前提:

- 製品の仕様は無い（利用者に見える機能を変えない、ハーネスの整備である）。
- 層、依存の向き、不変条件は変えない（`ARCHITECTURE.md` は読むだけ）。関係する ADR は、秘匿値の検査の範囲
  `docs/adr/0002-secret-scan-scope.md`（走査の公開の検査で、同じ secretlint の設定を使う）。新しい判断は `docs/adr/0006-drift-scan.md` に書く。
- 品質目標の「現在の評価」の節と検査の識別子の列は、先の変更（PR #34。計画 `2026-10-16-quality-score-current.md`）で入った。
- `AGENTS.md`、`package.json`、`.github/`、`scripts/harness/` は、評価の作業場所に写されるファイルなので、製品の機能の名前や
  記事の取得の方式を書かず、`docs/adr/` と `docs/exec-plans/` へリンクを張らない（パスは文字で書く）。

## 発見

- 秘匿値の検査の本体 `scripts/harness/check-secrets.mjs` は、調べるファイルを引数で受け取らない（作業ツリーかコミットの範囲だけ）。
  そこで、走査の公開の検査は、同じ設定（`.secretlintrc.json`）で secretlint を直接呼ぶ形にした（新しい依存は足していない）。
- secretlint は、`--format json --output <ファイル>` で書き出すと、規則に当たる値があっても終了コード 0 で終わる。走査は、書き出した
  結果の `messages` の数で判定する。
- TD-5 を消すと、技術的負債の一覧の表は行が 0 になる。走査は、行が無いことを `3/なし`（参考）の 1 行で書く。
- 走査の手元の実行の所要時間の大半は `test:harness` の段（約 150 秒）である。

## 判断の記録

1. 試験のための差し替えの環境変数の名前は、`DRIFT_SCAN_TEST_TODAY`（基準の日）と `DRIFT_SCAN_TEST_STAGES`（「<段>=<終了コード>」を
   空白で区切る。書かない段は 0）にした。どちらかが付いていれば、報告の `5/試験の差し替え` が「あり」で要対応になる。
2. そのため、試験の通る場合の期待する集合は、場合ごとの集合に `5/試験の差し替え` を足したものにした。「計画が 0 件で段が
   すべて成功する見本は要対応の集合が空」は、差し替えの行を除いた集合が空、という意味で確かめる。
3. `--out` は、無い置き場か空のディレクトリだけを受け取り、ほかは終了コード 2 にした。前の報告やほかのファイルを、成果物に
   混ぜないためである。置き場は、段を実行し終えた後に作る（CI で置き場がリポジトリの中にあっても、段の検査の対象にならない）。
4. `git fetch origin main` に失敗したときは、手元の追跡ブランチ `origin/main` の値を使い、報告の値にそのことを書く。追跡ブランチも
   無ければ終了コード 2 にする。手元でネットワークが無くても走査できるようにするためである。
5. 公開の検査の絶対パスの形は、パスの区切りの直後でない位置から始まるものだけにした（`src/var/` のような相対のパスを誤って
   当てないため）。`GITHUB_WORKSPACE` と `RUNNER_TEMP` の値は、文字列のまま探す。
6. 技術的負債の行の場所にバッククォートで囲んだパスが無いときは、「無い（場所を読めない）」として要対応にした。場所のファイルを
   確かめられないためである。
7. 品質目標の行の識別子は、名前のセル（領域か層）からバッククォートを外し、前後の空白を除いたものにした（例 `4/層:src/app/`）。
   報告の表の中で、識別子をバッククォートで囲んで書くためである。項目 4 には、要対応の理由を決まった文言で書く列を足し、`4/表` には、
   読めなかった行の行番号と決まった文言の理由だけを書く（文書の本文を写さない）。
8. 報告の書式の説明は、項目 1〜4 の表の後の節「この報告の書式」に書いた（1 行めの件数、次に項目 5、続けて項目 1〜4、の順を変えないため）。
9. cron から間隔の日数を求めるのは、毎日（分 時 * * *）と毎週（分 時 * * 曜日）の形だけにし、ほかの形は終了コード 2 にした。
   `DRIFT_SCAN_RETENTION_DAYS` は、1〜90 の整数でなければ終了コード 2 にした。契機の名前は、`schedule`、`workflow_dispatch`、
   `pull_request` 以外を「その他」と書く。

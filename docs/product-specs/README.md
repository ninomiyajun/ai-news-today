# 製品の仕様（書式と目録）

このプロジェクトの製品の仕様の書式と目録の正本。仕様は、何を、なぜ作るかを、利用者に見える振る舞いとして書く。
どう作るか（ライブラリ、ファイル、関数、層、データの持ち方）と作業の手順は仕様に書かず、仕様を引く計画に書く
（[計画の書式](../PLANS.md)）。製品の目的、対象の利用者、作らないものは [製品の前提](../PRODUCT_SENSE.md) にある。

## 置き場と名前

- 仕様は 1 機能 1 ファイルで、このディレクトリの直下に `<名前>.md` で置く（例: `list-font-size.md`）。名前は英小文字、
  数字、ハイフンだけで書き、英小文字か数字で始める。
- このファイル（`README.md`）は書式と目録で、仕様ではない。
- 仕様を書くのは仕様の担当で、承認するのは利用者である。仕様の担当は、このディレクトリの下（仕様のファイルと、下の
  「目録」の節の行）だけを書き換える。この文書の目録の節より前の部分と、製品の前提は書き換えない。

## 必須の節

仕様のファイルには、題（`# <題>`）の後に、次の 5 つの見出しを、この文字列のまま、すべて置く。書くことがまだ無い節も、
見出しは消さない。`npm run check:docs` は、この一覧の各行の、バッククォートで囲んだ見出しを読み取って照合する。

1. `## 目的`: 何を、なぜ作るか。利用者のどんな困りごとを解くか。
2. `## 利用者の操作の流れ`: 利用者が何をして、画面に何が出るかの流れ。
3. `## 受け入れ基準`: 下の「受け入れ基準の書式」に従う。
4. `## 画面と Figma の対応`: 画面ごとに、対応する Figma のフレームの名前かリンク。Figma が無いときは、無いことを書く。
5. `## 未決の点`: 利用者が決める点を、1 つずつ `[NEEDS CLARIFICATION: 具体的な質問]` の形で書く。推測で埋めない。
   無ければ「なし」と書く。

## 受け入れ基準の書式

- 基準ごとに `### <識別子> <題>` の見出しを置く。識別子の後に空白を 1 つ以上置き、題を書く。識別子は `<略号>-<数字>`
  （例: `FONT-1`）とする。略号は、下の目録で仕様ごとに決める英大文字 2〜6 字で、数字は 1 から振る。略号を 2 字以上にするのは、
  計画の中で振る識別子 `V<数字>` と区別するためである。
- 識別子は、同じ仕様の中でも、仕様をまたいでも重ねない。いちど振った識別子は消さず、別の基準に使い回さない。
- 見出しの下に、`- 前提:`、`- 操作:`、`- 期待する結果:` の行を 1 行ずつ置く。基準は、具体的な入力と出力を伴う振る舞いとして
  書く。
- 確かめ方は書かない。確かめ方は、仕様を引く計画の検証の節が書く（同じ基準を 2 か所に持たないため）。
- ``` で囲んだコードブロックの中の行は、見出しにも基準にも数えない。

例:

```markdown
### FONT-1 文字の大きさを「大」にすると、一覧の文字が大きくなる

- 前提: 一覧が標準の文字の大きさで表示されている。
- 操作: 文字の大きさの切り替えで「大」を選ぶ。
- 期待する結果: 一覧の各項目の題が、標準より大きい文字で表示される。切り替えには「大」が選ばれた状態で表示される。
```

## 状態の決まり

- 仕様の状態は、下の目録の「状態」の列だけに持つ。仕様のファイルに状態の行（`状態:` で始まる行）を書かない。
- 値は次の 3 つのどれか 1 語である。
  - `draft`: 下書き。利用者の承認の前。
  - `approved`: 利用者が承認した。
  - `archived`: 使わなくなった（新しい仕様に置き換えた、など）。
- 新しい仕様は、`draft` で目録に 1 行を足す。
- `draft` から `approved` に変えるのは、利用者が承認した後で、未決の点（`[NEEDS CLARIFICATION:`）が残っていないときだけである。
  計画は `approved` の仕様だけを引く（承認の前に計画を書かない）。
- `approved` の仕様の中身を変えるときは、次の 2 つに分ける。
  - その仕様を引く完了した計画（`docs/exec-plans/completed/`）が無いとき: 状態を `draft` に戻し、利用者の承認をやり直す。
  - その仕様を引く完了した計画があるとき: 仕様の中身を書き換えず、新しい略号で新しい仕様を作って `draft` で目録に足す。
    古い仕様は、利用者の指示があれば `archived` にする。完了した計画と受け入れ確認の記録が確かめた基準の中身を、後から
    変えないためである。
- この文書の書式（必須の節など）を変えたときに、それに合わせて既存の仕様へ見出しと空の項目を足すことは、中身の書き換えに
  数えない（承認のやり直しも、新しい仕様も要らない）。`archived` の仕様は、書式を変えた後も直さなくてよい（下の
  「`npm run check:docs` が確かめること」のとおり、書式を調べない）。
- `archived` に変えるのは、利用者の指示があるときだけである。

## 計画から仕様を引く形

計画の側の決まり（目的の節に書く仕様のパスの形、検証の節で仕様の識別子を引く形、引ける仕様の状態、`npm run check:docs` が
計画について失敗にすること）の正本は、[計画の書式](../PLANS.md) の「検証の節の書式」である。

## `check-docs.sh` が直接読む書式

`scripts/harness/check-docs.sh` は、次の書式をこの文書の文面から読み取らず、スクリプトの中に直接持っている。**どれかを変える
ときは、同じ変更で `scripts/harness/check-docs.sh` と、その試験 `scripts/harness/check-docs.test.sh` も直す。**

- 目録の表の見出しの行: 列の名前と順序が「略号、仕様、題、状態」の 4 列。各行も 4 列。
- 目録の仕様の欄: 仕様のファイル名を角括弧で囲み、その直後に同じファイル名を丸括弧で囲んで続けるインラインのリンク。
- 仕様のファイルの名前: 英小文字、数字、ハイフン（計画の目的の節のパスを拾うときに使う）。
- 略号の形: 英大文字 2〜6 字。識別子の形: `<略号>-<数字>`。
- 受け入れ基準の節の見出し `## 受け入れ基準`、基準の見出し `### <識別子> <題>`、項目の行 `- 前提:`、`- 操作:`、`- 期待する結果:`。
- 状態の値: `draft`、`approved`、`archived`。仕様の中の状態の行の形（`状態:` または `- 状態:` で始まる行）。
- 未決の点の印: `[NEEDS CLARIFICATION:`。
- 目録の節の見出し `## 目録` と、必須の節の一覧の見出し `## 必須の節` と、その一覧の行の形（番号、ピリオド、空白、バッククォートで
  囲んだ見出し。`docs/PLANS.md` の「必須の節」と同じ形）。

## `npm run check:docs` が確かめること

このディレクトリがあるときは、次を失敗にする。

- 目録の表が無い。目録の表の見出しの行が上の形でない。4 列でない目録の行。
- 英小文字・数字・ハイフンでない仕様のファイル名（目録のリンク先と、このディレクトリの直下の `*.md` の両方）。
- 目録に無い仕様のファイル、実在しない仕様を指す目録の行、このディレクトリの直下の `*.md` でないリンク先、同じ仕様を指す
  2 つ以上の目録の行。
- 英大文字 2〜6 字でない略号、重複した略号。
- `draft`、`approved`、`archived` のどれでもない状態。仕様のファイルの中の状態の行。
- `approved` と `archived` の仕様に残る `[NEEDS CLARIFICATION:`。
- 上の「必須の節」の見出しの欠け。
- 受け入れ基準の見出しが 1 つも無い仕様。仕様の略号で始まる `<略号>-<数字>` の形でない識別子。題の無い基準の見出し。
  前提・操作・期待する結果の行が無い、または 2 行以上ある基準。
- 同じ仕様の中、または仕様をまたいで重複した識別子。

`archived` の仕様には、必須の節と、受け入れ基準の書式（基準の数、識別子の形、題、項目の行）を調べない。識別子は集めて、
重複と、完了した計画が引く識別子の実在の確認に使う。

計画の側で失敗にすることは、[計画の書式](../PLANS.md) の「検証の節の書式」にある。仕様と計画のどちらも、``` で囲んだ
コードブロックの中の行は数えない。

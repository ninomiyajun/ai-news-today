## 気づいたこと

- 2 回目は、2 時間以内に完了の報告まで進んだ（P2 の課題 A は 2 時間で終わらなかった）。ただし試行は各段階 1 回ずつで、Claude Code の版と環境変数も P2 と違うので、これを P3 の効果とは言い切れない。
- 採点用の試験の不合格 3 件は、同じ 1 つの原因による。エージェントが `src/composition/runtime.ts` に `server-only`（サーバーの外から読み込むと失敗させる部品）を足したため、試験の環境からこのファイルを読み込めなくなった。エージェント自身の試験は、このファイルを読み込まない形で書かれていたので、この失敗に気づかなかった。design-reviewer はこの構成を妥当と評価し、試験から使えなくなる点は指摘しなかった。この見落としを、design-reviewer の手順書の点検の観点を見直す材料にする。
- `npm run check` の不合格は、試験の項目の 1 件だけである。エージェントの試験の準備のファイル（vitest の `setupFiles` に指定したもの）が採点の環境では読み込まれず、その準備を前提にした試験が失敗した。採点の環境の限界によるもので、エージェントの作業の誤りとは扱わない。1 回目の不合格も同じ形である。
- 1 回目は、Claude Code が裏で動く処理の終わりを待つ時間の上限（600 秒）に達して打ち切られた。対話をしない実行（`claude -p`）では、この上限で実行そのものが終わる。対処として、試行を起動するスクリプトで `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` を付けるようにし、2 回目はこの設定で実行した。
- 2 回目の計画のファイルでは、design-reviewer の指摘をそれぞれ採るか採らないかと、その理由が、判断の記録に書かれていた。

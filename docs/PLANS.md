# 計画の書式

このプロジェクトの実行計画（ExecPlan）の書式の正本。計画をファイルに書く条件、置き場所と名前、書き方の原則、
必須の節を定める。受け入れ確認の記録の書式は、まだ定めていない。

## 計画をファイルに書く条件

次のどれか 1 つに当たる作業は、計画をファイルに書く。当たるかどうか迷うときは、書く側に倒す。

- 構成やインターフェースを変える。構成は、`ARCHITECTURE.md` に書いた層の分け方と依存の向きを指す。
  インターフェースは、外から使われる境界を指す。公開の API、CLI、データの形式（ファイルの書式、データベースの
  スキーマ、通信の形式）と、`ARCHITECTURE.md` が層の境界として定めたものが当たる。
- 3 つ以上の層に影響する。層は、`ARCHITECTURE.md` の「層と責務」の表の 1 行を 1 つと数える。
- データベースのマイグレーションを伴う。
- 手順の間に順序の依存がある。前の手順を終えないと、次の手順に進めない関係を指す。
- 1 回のエージェントのセッションの中で、完了まで進められない見込みである。

## 置き場所と名前

- 新しい計画は、`docs/exec-plans/active/YYYY-MM-DD-<題>.md` に置く。
- 作業を終えたら、「結果と振り返り」の節を書いてから、`docs/exec-plans/completed/` へ移す。
- 計画の状態（進行中、完了）は、置いたディレクトリで表し、ファイルの中には書かない。
- `npm run check:docs` は、この 2 つのディレクトリの直下にある `.md` のファイルを、すべて計画とみなして、
  下の「必須の節」が揃っているかを確かめる。

## 書き方の原則

- その 1 ファイルだけを読んだ初めての人が、作業を再開して完了まで進められるように書く。会話の中にしか無い
  前提、決定、用語を残さず、計画に書く。
- 分からない点は `[NEEDS CLARIFICATION: 具体的な質問]` と書き、推測で埋めない。
- 完了の条件は、「検証（完了の条件）」の節の 1 か所にだけ書く。製品の仕様があるときは、仕様の受け入れ基準を
  識別子で引き、仕様の文面は書き写さない。仕様の無い作業（不具合の修正、内部の整理）では、基準をこの節に
  直接書く。
- 「進捗」「発見」「判断の記録」の節は、作業の区切りごとに更新する。作業が中断しても、別の人が計画だけを
  読んで再開できるようにするためである。
- 方針を決めたら、決める前に書いた下書きの指示の文（「〜を調べて決める」「決めた形をここに書く」など）を、
  決めた内容の文に置き換えるか、消す。手順の節の文も対象である。決めた理由は「判断の記録」に書く。指示の文が
  残っていると、再開する人が、まだ決まっていないと読み違えるためである。

## 必須の節

計画のファイルには、次の 8 つの見出しを、この文字列のまま、すべて置く。書くことがまだ無い節も、見出しは消さない。
「作業の場所」は、題の直後に、最初の節として置く。
`npm run check:docs` は、この一覧の各行の、バッククォートで囲んだ見出しを読み取って照合する。一覧の行の形
（番号、ピリオド、空白、バッククォートで囲んだ見出し）を変えるときは、`scripts/harness/check-docs.sh` も直す。

1. `## 作業の場所`: 作業するブランチの名前と、worktree のディレクトリ名。計画と作業中の変更は、コミットするまで
   その worktree の中にしか無いので、この節は worktree を探す手がかりにはならない。この節の役割は、見つけた
   worktree が正しいかを確かめることと、worktree を作り直したときに場所を引き継ぐことである。
   - パスは書かず、worktree のディレクトリ名（例: `wt-<名前>`）とブランチの名前だけを書く。ホームの下だけでなく
     一時ディレクトリのパスにもアカウント名が入るためである（`AGENTS.md` の「秘匿値と個人情報」）。リポジトリ
     本体で作業するときは、そう書く。
   - 書く前に、ブランチの名前と worktree のディレクトリ名に、個人情報（アカウント名、姓名、メールアドレス）が
     含まれないことを確かめる。含むときは、一般的な名前に付け直してから書く。
   - 再開する人は、リポジトリで `git worktree list` を実行し、各 worktree の `docs/exec-plans/active/` を見て計画を
     探す。見つけた計画のこの節と、その worktree のディレクトリ名とブランチの名前が一致することを確かめる。
   - worktree を作り直したり、ブランチを変えたりしたら、この節を直す。
2. `## 目的`: 何を、なぜ行うか。前提として、製品の仕様があればそのパスを、関係する `ARCHITECTURE.md` の箇所と
   ADR を書く。仕様や関係する ADR が無いときは、無いことを書く。
3. `## 検証（完了の条件）`: 基準ごとに、前提、操作、期待する結果、確かめ方（自動テスト、人が確認など）を書く。
   基準は、具体的な入力と出力を伴う振る舞いとして書く。
4. `## 手順`: 作業の順序。
5. `## 進捗`: 終えた手順とその日時、残っている手順。手順の途中で区切るときは、日時の行に次の 3 つも書く。
   - その手順の中で終えたこと（例: 書いた試験の件数と、通ったかどうか。直し終えたファイル）。
   - その手順の中で残っていること（例: まだ直していないファイル）。
   - 未コミットの変更があるファイルと、それぞれ何を変えたか。未コミットの変更が無いときは、無いと書く。

   例: 「2026-10-06: 手順 3 の途中で区切った。終えたこと: 基準 1〜3 の試験を 5 件書き、すべて通った。残り:
     `src/curation/a.ts` の修正。未コミットの変更: `src/curation/a.test.ts`（試験 5 件の追加）。」
6. `## 発見`: 作業の途中で分かった、計画の前提と違う事実。
7. `## 判断の記録`: 作業の途中で決めたことと、その理由。合意の後に完了の条件を変えたときも、ここに理由を書く。
8. `## 結果と振り返り`: 計画を閉じるときに書く。残す価値のある設計判断は、`docs/adr/` に ADR として書く。
   閉じるときは、「作業の場所」の節に、作業を終えた時点のブランチの名前と worktree のディレクトリ名をそのまま
   残す。計画はマージより前に閉じるので、マージと worktree の片付けは最終の報告に書き、計画には書かない。

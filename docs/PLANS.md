# 計画の書式

このプロジェクトの実行計画（ExecPlan）の書式の正本。計画をファイルに書く条件、置き場所と名前、書き方の原則、
必須の節を定める。受け入れ確認の記録の書式は、まだ定めていない。

## 計画をファイルに書く条件

次のどれか 1 つに当たる作業は、計画をファイルに書く。当たるかどうか迷うときは、書く側に倒す。

- 構成やインターフェースを変える。構成は、`ARCHITECTURE.md` に書いた層の分け方と依存の向きを指す。
  インターフェースは、外から使われる境界を指す。公開の API、CLI、データの形式（ファイルの書式、データベースの
  スキーマ、通信の形式）と、`ARCHITECTURE.md` が層の境界として定めたものが当たる。
- 3 つ以上の層に影響する。層は、`ARCHITECTURE.md` の「層と責務」の表の 1 行を 1 つと数える。
- データベースのマイグレーションを伴う。
- 手順の間に順序の依存がある。前の手順を終えないと、次の手順に進めない関係を指す。
- 1 回のエージェントのセッションの中で、完了まで進められない見込みである。

## 置き場所と名前

- 新しい計画は、`docs/exec-plans/active/YYYY-MM-DD-<題>.md` に置く。
- 作業を終えたら、「結果と振り返り」の節を書いてから、`docs/exec-plans/completed/` へ移す。
- 計画の状態（進行中、完了）は、置いたディレクトリで表し、ファイルの中には書かない。
- `npm run check:docs` は、この 2 つのディレクトリの直下にある `.md` のファイルを、すべて計画とみなして、
  下の「必須の節」が揃っているかを確かめる。

## 書き方の原則

- その 1 ファイルだけを読んだ初めての人が、作業を再開して完了まで進められるように書く。会話の中にしか無い
  前提、決定、用語を残さず、計画に書く。
- 分からない点は `[NEEDS CLARIFICATION: 具体的な質問]` と書き、推測で埋めない。
- 完了の条件は、「検証（完了の条件）」の節の 1 か所にだけ書く。製品の仕様があるときは、仕様の受け入れ基準を
  識別子で引き、仕様の文面は書き写さない。仕様の無い作業（不具合の修正、内部の整理）では、基準をこの節に
  直接書く。
- 「進捗」「発見」「判断の記録」の節は、作業の区切りごとに更新する。作業が中断しても、別の人が計画だけを
  読んで再開できるようにするためである。

## 必須の節

計画のファイルには、次の 7 つの見出しを、この文字列のまま、すべて置く。書くことがまだ無い節も、見出しは消さない。
`npm run check:docs` は、この一覧の各行の、バッククォートで囲んだ見出しを読み取って照合する。一覧の行の形
（番号、ピリオド、空白、バッククォートで囲んだ見出し）を変えるときは、`scripts/harness/check-docs.sh` も直す。

1. `## 目的`: 何を、なぜ行うか。前提として、製品の仕様があればそのパスを、関係する `ARCHITECTURE.md` の箇所と
   ADR を書く。仕様や関係する ADR が無いときは、無いことを書く。
2. `## 検証（完了の条件）`: 基準ごとに、前提、操作、期待する結果、確かめ方（自動テスト、人が確認など）を書く。
   基準は、具体的な入力と出力を伴う振る舞いとして書く。
3. `## 手順`: 作業の順序。
4. `## 進捗`: 終えた手順とその日時、残っている手順。
5. `## 発見`: 作業の途中で分かった、計画の前提と違う事実。
6. `## 判断の記録`: 作業の途中で決めたことと、その理由。合意の後に完了の条件を変えたときも、ここに理由を書く。
7. `## 結果と振り返り`: 計画を閉じるときに書く。残す価値のある設計判断は、`docs/adr/` に ADR として書く。

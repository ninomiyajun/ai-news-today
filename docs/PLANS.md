# 計画の書式

このプロジェクトの実行計画（ExecPlan）の書式の正本。計画をファイルに書く条件、置き場所と名前、書き方の原則、
必須の節、検証の節の書式、受け入れ確認の記録の書式を定める。

## 計画をファイルに書く条件

次のどれか 1 つに当たる作業は、計画をファイルに書く。当たるかどうか迷うときは、書く側に倒す。

- 構成やインターフェースを変える。構成は、`ARCHITECTURE.md` に書いた層の分け方と依存の向きを指す。
  インターフェースは、外から使われる境界を指す。公開の API、CLI、データの形式（ファイルの書式、データベースの
  スキーマ、通信の形式）と、`ARCHITECTURE.md` が層の境界として定めたものが当たる。
- 3 つ以上の層に影響する。層は、`ARCHITECTURE.md` の「層と責務」の表の 1 行を 1 つと数える。
- データベースのマイグレーションを伴う。
- 手順の間に順序の依存がある。前の手順を終えないと、次の手順に進めない関係を指す。
- 1 回のエージェントのセッションの中で、完了まで進められない見込みである。

## 置き場所と名前

- 新しい計画は、`docs/exec-plans/active/YYYY-MM-DD-<題>.md` に置く。
- 作業を終えたら、「結果と振り返り」の節を書いてから、`docs/exec-plans/completed/` へ移す。
- 計画の状態（進行中、完了）は、置いたディレクトリで表し、ファイルの中には書かない。
- `npm run check:docs` は、この 2 つのディレクトリの直下にある `.md` のファイルのうち、名前が `.acceptance.md` で
  終わらないものを、すべて計画とみなして、下の「必須の節」が揃っているかを確かめる。名前が `.acceptance.md` で終わる
  ファイルは受け入れ確認の記録（下の「受け入れ確認の記録」）である。

## 書き方の原則

- その 1 ファイルだけを読んだ初めての人が、作業を再開して完了まで進められるように書く。会話の中にしか無い
  前提、決定、用語を残さず、計画に書く。
- 分からない点は `[NEEDS CLARIFICATION: 具体的な質問]` と書き、推測で埋めない。
- 完了の条件は、「検証（完了の条件）」の節の 1 か所にだけ書く。製品の仕様があるときは、仕様の受け入れ基準を
  識別子で引き、仕様の文面は書き写さない。仕様の無い作業（不具合の修正、内部の整理）では、基準をこの節に
  直接書く。
- 「進捗」「発見」「判断の記録」の節は、作業の区切りごとに更新する。作業が中断しても、別の人が計画だけを
  読んで再開できるようにするためである。
- 方針を決めたら、決める前に書いた下書きの指示の文（「〜を調べて決める」「決めた形をここに書く」など）を、
  決めた内容の文に置き換えるか、消す。手順の節の文も対象である。決めた理由は「判断の記録」に書く。指示の文が
  残っていると、再開する人が、まだ決まっていないと読み違えるためである。

## 必須の節

計画のファイルには、次の 8 つの見出しを、この文字列のまま、すべて置く。書くことがまだ無い節も、見出しは消さない。
「作業の場所」は、題の直後に、最初の節として置く。
`npm run check:docs` は、この一覧の各行の、バッククォートで囲んだ見出しを読み取って照合する。一覧の行の形
（番号、ピリオド、空白、バッククォートで囲んだ見出し）を変えるときは、`scripts/harness/check-docs.sh` も直す。

1. `## 作業の場所`: 作業するブランチの名前と、worktree のディレクトリ名。計画と作業中の変更は、コミットするまで
   その worktree の中にしか無いので、この節は worktree を探す手がかりにはならない。この節の役割は、見つけた
   worktree が正しいかを確かめることと、worktree を作り直したときに場所を引き継ぐことである。
   - パスは書かず、worktree のディレクトリ名（例: `wt-<名前>`）とブランチの名前だけを書く。ホームの下だけでなく
     一時ディレクトリのパスにもアカウント名が入るためである（`AGENTS.md` の「秘匿値と個人情報」）。リポジトリ
     本体で作業するときは、そう書く。
   - 書く前に、ブランチの名前と worktree のディレクトリ名に、個人情報（アカウント名、姓名、メールアドレス）が
     含まれないことを確かめる。含むときは、一般的な名前に付け直してから書く。
   - 再開する人は、リポジトリで `git worktree list` を実行し、各 worktree の `docs/exec-plans/active/` を見て計画を
     探す。見つけた計画のこの節と、その worktree のディレクトリ名とブランチの名前が一致することを確かめる。
   - worktree を作り直したり、ブランチを変えたりしたら、この節を直す。
2. `## 目的`: 何を、なぜ行うか。前提として、製品の仕様があればそのパス（`docs/product-specs/<名前>.md` の形）を、関係する `ARCHITECTURE.md` の箇所と
   ADR を書く。仕様や関係する ADR が無いときは、無いことを書く。
3. `## 検証（完了の条件）`: 基準ごとに、前提、操作、期待する結果、確かめ方（自動テスト、人が確認など）を書く。
   基準は、具体的な入力と出力を伴う振る舞いとして書く。新しい書式を適用する計画は、下の「検証の節の書式」に従う。
4. `## 手順`: 作業の順序。
5. `## 進捗`: 終えた手順とその日時、残っている手順。手順の途中で区切るときは、日時の行に次の 3 つも書く。
   - その手順の中で終えたこと（例: 書いた試験の件数と、通ったかどうか。直し終えたファイル）。
   - その手順の中で残っていること（例: まだ直していないファイル）。
   - 未コミットの変更があるファイルと、それぞれ何を変えたか。未コミットの変更が無いときは、無いと書く。

   例: 「2026-10-06: 手順 3 の途中で区切った。終えたこと: 基準 1〜3 の試験を 5 件書き、すべて通った。残り:
     `src/curation/a.ts` の修正。未コミットの変更: `src/curation/a.test.ts`（試験 5 件の追加）。」
6. `## 発見`: 作業の途中で分かった、計画の前提と違う事実。
7. `## 判断の記録`: 作業の途中で決めたことと、その理由。合意の後に完了の条件を変えたときも、ここに理由を書く。
8. `## 結果と振り返り`: 計画を閉じるときに書く。残す価値のある設計判断は、`docs/adr/` に ADR として書く。
   閉じるときは、「作業の場所」の節に、作業を終えた時点のブランチの名前と worktree のディレクトリ名をそのまま
   残す。計画はマージより前に閉じるので、マージと worktree の片付けは最終の報告に書き、計画には書かない。

## 検証の節の書式

次の 1 行に書いた日付以降の日付をファイル名に持つ計画（新しい書式の計画）は、「検証（完了の条件）」の節をこの書式で書く。
それより前の日付の計画（旧い書式の計画）は、書き直さなくてよい。`npm run check:docs` はこの行の日付を読み取って、
受け入れ確認の記録を検査する計画を決める（行の形を変えるときは `scripts/harness/check-docs.sh` も直す）。

新しい書式の適用開始: 2026-10-07

- 基準ごとに `### <識別子> <題>` の見出しを置く。識別子は、計画の中で振る `V<数字>`（`V1`、`V2` など）か、製品の仕様の
  受け入れ基準の識別子とする。識別子に空白を含めず、同じ計画の中で重ねない。製品の仕様の受け入れ基準の識別子は
  `<略号>-<数字>` の形である（`docs/product-specs/README.md`）。
- 製品の仕様の識別子を引く計画は、目的の節に、引く仕様のパスをリポジトリの根からの `docs/product-specs/<名前>.md` の形で
  書く（`<名前>` は英小文字、数字、ハイフン。仕様の書式と目録の正本は `docs/product-specs/README.md`）。仕様が 2 つ以上なら、
  パスを並べて書く。計画は、目録の状態が `approved` の仕様だけを引く（承認の前に計画を書かない）。
- `npm run check:docs` は、`active/` と `completed/` の新しい書式の計画について、次を失敗にする（仕様の置き場
  `docs/product-specs/` が無くても働く）。
  - `V<数字>` でない識別子が、どの仕様の受け入れ基準にも無い（仕様の置き場が無ければ、`V<数字>` でない識別子はすべて失敗）。
  - 目的の節に書いた仕様と、検証の節の識別子の所属先の仕様の状態が、進行中の計画では `approved` でない、完了した計画では
    `approved` でも `archived` でもない（完了した後に仕様が新しい仕様に置き換わって `archived` になっても、過去の計画を失敗に
    しないため）。
  - 仕様の識別子を引くのに、目的の節に仕様のパスが無い。目的の節に書いた仕様のパスが目録に無い。識別子の所属先の仕様が、
    目的の節に書いた仕様のどれでもない。
- 見出しの下に、`- 前提:`、`- 操作:`、`- 期待する結果:`、`- 確かめ方:` の行を置く。確かめ方は「自動テスト」「受け入れ確認」
  「人が確認」のどれか 1 語だけを書く。受け入れ確認は、動いているアプリを、実装した本人とは別の受け入れ確認の担当が操作して
  確かめることを指す。
- 確かめ方の行は、行の頭から `- 確かめ方: <値>` の形のまま書き（半角のコロンと空白。字下げや別の箇条書きの記号を使わない）、
  各見出しの下にちょうど 1 行置く。
- 確かめ方が受け入れ確認の基準には、`- 対象ファイル:` の行に、確かめる対象のファイルを並べる。省略したときは、
  下の「確かめた対象の特定」の、計画が対象を書かないときの範囲を対象にする。
- ``` で囲んだコードブロックの中の行は、基準にも確かめ方にも数えない。コードブロックは必ず閉じる。

`completed/` にある、新しい書式の計画では、`npm run check:docs` が検証の節について次を失敗にする（ファイル名が日付で
始まらない計画も、新しい書式の計画として扱う）。

- 確かめ方の行が、どの `### <識別子>` の見出しの下にも無い（どの基準の確かめ方かが決まらないため）。
- 見出しの下に確かめ方の行が無い、または 2 行以上ある。確かめ方の値が上の 3 つのどれでもない。
- 識別子が重複している。識別子の無い見出しがある。
- 「確かめ方」の語の後に `:` か `：` が続くのに、上の形に一致しない行（全角のコロン、字下げ、別の箇条書きの記号など）。
- 「確かめ方」と「受け入れ確認」の両方を含むのに、上の形に一致しない行（コロンの無い行など）。
- 「受け入れ確認」を含む表の行（受け入れ確認の基準は、表ではなく見出しと確かめ方の行で書く）。地の文と、ほかの項目の
  行（`- 期待する結果:` など）で受け入れ確認に触れるだけの行は対象にしない。
- 基準の見出し（`### <識別子> <題>`）が 1 つも無い。
- 閉じていないコードブロック（``` の行の数が奇数）。

例:

```markdown
### V1 決まった記事が点数の高い順に並ぶ

- 前提: 確認用のデータで起動している。
- 操作: 画面を開く。
- 期待する結果: 記事が点数の高い順に並ぶ。
- 確かめ方: 受け入れ確認
- 対象ファイル: `src/ui/NewsList.tsx`
```

## 受け入れ確認の記録

確かめ方が受け入れ確認の基準を、受け入れ確認の担当が確かめた結果の記録。担当は、このファイルだけに書き込む。

### 置き場と名前

- 計画と同じディレクトリに、`<計画のファイル名から .md を除いたもの>.acceptance.md` の名前で置く
  （例: `2026-10-08-score-filter.md` の記録は `2026-10-08-score-filter.acceptance.md`）。
- 計画を `completed/` へ移すときは、記録も同じ変更で移す。
- `npm run check:docs` は、新しい書式の計画のうち `completed/` にあるものについて、次を失敗にする: 受け入れ確認の基準が
  あるのに記録が無い／判定に数える実行が 1 件も無い基準がある／基準ごとの最新の結果が「合格」でない／記録が下の
  「書式」の必須の決まりに合わない。あわせて、
  `active/` と `completed/` のどちらでも、同じ名前の計画が無い記録、計画と別のディレクトリにある記録、絶対パスの形
  （`/Users/`、`/home/`、`/private/`、`/tmp/`、`/var/folders/`）を含む記録を失敗にする。

### 書式

確かめるたびに、ファイルの末尾に `## 実行 <番号>` の節を 1 つ足す。各実行の節には、次の例の行をこの形のまま置く。
行の頭の `- ` と、項目の名前の後の `: ` は変えない（`npm run check:docs` が読み取るため）。

**必須の決まり**（`npm run check:docs` が確かめる。合わなければ失敗にする）:

- `## ` の見出しは `## 実行 <番号>` だけを使う。番号は 1 から始め、欠けずに 1 ずつ増やす。実行の節は 1 つ以上置く。
- 各実行の節に、次の 8 つの行をちょうど 1 行ずつ置く: `- 日時:`、`- 確かめた者:`、`- 元のコミット:`、`- 分岐元:`、
  `- 確かめた対象:`、`- 基準外の所見:`、`- 未確認の範囲:`、`- 全体:`。`- 確かめた対象:` 以外は、同じ行に値を書く
  （`- 確かめた対象:` の値は、その下の字下げした行に並べる）。無いときも「なし」と書き、行を省かない。
- `- 全体:` の値は `合格`、`不合格`、`未確認` のどれか 1 語。
- 各実行の節に `- 基準 <識別子>: <結果>` の行を 1 つ以上置き、各行の下に、字下げした `- 証拠: <値>` の行を置く。
- ``` で囲んだコードブロックは必ず閉じる。

前提・操作・観察した結果の行も、基準ごとに書く（検査はしないが、再現と見直しに要るため）。

```markdown
# 受け入れ確認の記録: 2026-10-08-score-filter

## 実行 1

- 日時: 2026-10-08 14:05（日本時間）
- 確かめた者: app-evaluator
- 元のコミット: <確かめた時点の git rev-parse HEAD の値>
- 分岐元: <git merge-base HEAD origin/main の値>
- 確かめた対象:
  - `src/ui/NewsList.tsx` <git hash-object の値> <状態>
- 基準 V1: 合格
  - 前提: 確認用のデータで、ポート 3100 で起動した。
  - 操作: 画面を開いた。
  - 観察した結果: 記事が 412、156、88、37 の順に並んだ。
  - 証拠: 画面の本文の抜き書き。スクリーンショット v1.png（一覧の全体が写っている）。
- 基準外の所見: なし
- 未確認の範囲: Figma との照合（照合する対象が無い）
- 全体: 合格
```

- `- 確かめた者:` には、確かめた担当の名前を書く。判定に数えるのは `app-evaluator` の実行だけで、ほかの名前の実行
  （実装した本人の自己確認など）は記録に残してよいが、合否の判定には数えない。
- `- 基準 <識別子>: <結果>` の結果は、`合格`、`不合格`、`未確認` のどれか 1 語だけを書く。確かめられなかった基準は
  `未確認` とし、全体を合格にしない。1 件でも `不合格` があれば全体を `不合格` とし、その基準の下に再現の手順と、
  分かれば該当のコードの場所を書く。
- 一部の基準だけを確かめ直した実行（部分の再確認）には、確かめ直した基準の行だけを書く。基準ごとの判定には、
  判定に数える実行のうち、その基準の行を持つ最も後の実行の結果を使う。
- 基準外の所見には、基準に当たらないが見つけた問題を書く。無ければ「なし」と書く。
- ``` で囲んだコードブロックの中の行は、記録に数えない（例として書いた行を、判定に使わないため）。

### 確かめた対象の特定

確かめる前に、次の手順で対象を特定し、「元のコミット」「分岐元」「確かめた対象」の行に書く。後で、どの内容を確かめたかを
コミットと比べられるようにするためである。

1. 元のコミット: 確かめる時点の `git rev-parse HEAD` の値。
2. 分岐元: `git merge-base HEAD origin/main` の値。作業のブランチが main から分かれたコミットで、対象の範囲の起点にする。
   元のコミットだけを起点にすると、同じブランチで先にコミットした変更が範囲から外れるためである。
3. 対象のファイル: 基準の `- 対象ファイル:` に書いたもの。計画が書かないときは、`git diff --name-only <分岐元>` と
   `git ls-files --others --exclude-standard` の出力の和（分岐元からのコミット済みの変更、未コミットの変更、未追跡のファイル）。
4. 対象のファイルごとに、パスの順に、作業ツリーの内容の `git hash-object -- <パス>` の値（ファイルが無ければ「なし」）と、
   `git status --porcelain=v1 --untracked-files=all -- <パス>` の出力の先頭の 2 文字（出力が空なら「変更なし」）を書く。
   内容のハッシュは、ステージ済み、未ステージ、未追跡のどれでも同じ値になり、コミットの後も
   `git rev-parse <コミット>:<パス>` の値と比べられる。

### 書いてはならないもの

- 絶対パス（ホームの下、一時ディレクトリの下のどちらも）。アカウント名が入るためである。パスはリポジトリの根からの
  相対で書く。
- 認証情報（パスワード、トークン、Cookie）、個人のメールアドレス、アカウントの識別子。
- スクリーンショットそのもの。スクリーンショットはリポジトリの外の一時ディレクトリに置き、記録にはファイル名と、
  写っているものだけを書く。

### 追記だけで書き換えない

- 記録には実行の節を末尾に足すだけで、前の実行の記述を書き換えたり消したりしない。誤りに気づいたら、新しい実行の節で
  確かめ直し、所見にその旨を書く。
- 担当は、書いた後の記録の全体のバイト数（`wc -c < <記録>`）と sha256（`shasum -a 256 < <記録>`）を報告する。
- 照合は、過去の各回の（バイト数, sha256）について、記録の先頭のそのバイト数の部分（`head -c <バイト数> <記録>`）の
  sha256 が、その回に報告した値と一致するかを比べる。追記だけなら全回が一致し、途中の回の範囲を書き換えると、
  その回とそれより後の回の照合が一致しなくなる。行数でなくバイト数を使うのは、行数では記録の末尾の改行の有無によって
  照合する範囲が食い違うためである。
